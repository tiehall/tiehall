# Making the repository public

The repository, at `github.com/tiehall/tiehall`, goes public once, as a new repository that holds the rewritten history, while the current one stays private as the archive (GP-10). This is the maintainers' checklist for that step: what the repository must hold and leave out, how its history is rewritten and checked, how GitHub is set up for a public project, and what follows the switch. The plan's tasks 30.1 to 30.6 carry it out ([the plan's group 30](../../openspec/changes/add-tiehall-oss-v1/tasks.md#30-making-the-repository-public)).

Each item says what to do and gives one or more `Evidence:` lines that link what shows the item holds: a check or a test of the repository, a file, a workflow, or GitHub's documentation of a setting together with the command that reads the setting back. An item marked as a founder step needs the founder's own accounts or permission at that time, and an agent working on the repository never does it: the history rewrite and its push, GitHub's settings and the switch to public. Nothing personal or secret may remain in the public repository, its history included.

### GP-23 The DNS records for tiehall.com at Turhost

A founder step, for the domain `tiehall.com`, whose DNS Turhost serves, and the organization `tiehall`. The records are GitHub Pages' own, so they are the same whether the page is served from this repository or from a repository of its own (GP-22), whose name then takes the place of `tiehall/tiehall` in the commands below.

- Before the switch, and before any record points at GitHub: verify the domain for the organization, under its Settings, Verified and approved domains, adding `tiehall.com` and, at Turhost, the TXT record whose name and value GitHub shows; and verify it for GitHub Pages, under the organization's Settings, Pages, adding `tiehall.com` and, at Turhost, the TXT record `_github-pages-challenge-tiehall.tiehall.com` with the value GitHub shows. Keep the second record in the zone for good: while it is there, no other account can publish a site on the domain.
- Read back: `dig +short TXT _github-pages-challenge-tiehall.tiehall.com` prints the value GitHub showed, the organization's Pages settings show `tiehall.com` as verified, and the organization's profile shows the Verified badge.
- Read back: `gh api graphql -f query='query { organization(login: "tiehall") { domains(first: 10) { nodes { domain isVerified } } } }'`, with the `admin:org` scope (`gh auth refresh -s admin:org`), lists `tiehall.com` with `"isVerified":true`.
- At the switch, once the repository is public (GP-19): turn GitHub Pages on for it, publishing from the workflow, `gh api -X POST repos/tiehall/tiehall/pages -f build_type=workflow`, and give it the custom domain, `gh api -X PUT repos/tiehall/tiehall/pages -f cname=tiehall.com`. GitHub Pages reads no CNAME file from a workflow's upload, so this setting is the domain, and `site/CNAME` records it beside the page.
- Then, in Turhost's DNS zone for `tiehall.com`, remove every other record at the apex (`@`) and for `www`, such as a parking page's `A` record or a forward, since any other `A`, `AAAA`, `ALIAS` or `ANAME` record at the apex keeps GitHub from getting a certificate, and any wildcard record (`*`), which GitHub warns lets another account take a subdomain over even once the domain is verified. Keep the TXT records of the verification. Then add:
  - at `@`, four `A` records: `185.199.108.153`, `185.199.109.153`, `185.199.110.153` and `185.199.111.153`;
  - at `@`, four `AAAA` records: `2606:50c0:8000::153`, `2606:50c0:8001::153`, `2606:50c0:8002::153` and `2606:50c0:8003::153`;
  - for `www`, a `CNAME` record to `tiehall.github.io`, the organization's own domain on GitHub Pages, without the repository's name.
- If the zone holds a `CAA` record, one of them allows `letsencrypt.org`, from which GitHub Pages takes the domain's certificate.
- Read back: `dig +short A tiehall.com` prints the four addresses, `dig +short AAAA tiehall.com` the four IPv6 addresses, and `dig +short CNAME www.tiehall.com` prints `tiehall.github.io.`. A change at Turhost can take up to a day to reach every resolver.
- GitHub then checks the records and asks Let's Encrypt for the certificate, which can also take up to a day: `gh api repos/tiehall/tiehall/pages/health` reads the check, and the repository's Pages settings show the domain with a check mark once the certificate exists. Only then enforce HTTPS: `gh api -X PUT repos/tiehall/tiehall/pages -F https_enforced=true -f cname=tiehall.com`.
- Then publish the page, since no push to `main` changes `site/` at the switch: `gh workflow run pages.yml --repo tiehall/tiehall`; read back `gh run list --repo tiehall/tiehall --workflow pages.yml --limit 1`, whose run passed.
- Read back: `gh api repos/tiehall/tiehall/pages --jq '{cname, https_enforced, build_type, status, certificate: .https_certificate.state}'` gives `"cname":"tiehall.com"`, `"https_enforced":true` and `"build_type":"workflow"`; `curl -sSI http://tiehall.com` answers with a redirect to `https://tiehall.com/`, and `curl -sSI https://www.tiehall.com` with one to `https://tiehall.com/`.
