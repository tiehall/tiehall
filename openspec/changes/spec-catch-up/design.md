# Design: Spec catch-up for D45 and D46

## Context

[proposal.md](proposal.md) says why the specs of `add-tiehall-oss-v1` are brought up to what the code does. This document restates the two decisions the deltas rest on, D45 and D46, item by item, as public rules: each with the rule, why it is right, the alternatives considered and why they lost, and where the code implements it. Nothing here is new behavior; where the code and the decision text differ, this document describes the code and says so.

**How the specs cite this document.** Every `Source:` line in `specs/*/spec.md` keeps, word for word, the citation the requirement carries in `add-tiehall-oss-v1`: its decision numbers and the sections of that change's design.md (`Decisions this change rests on`, `Design rules: …`, `Technical decisions: …` and `Self-hosting decisions: …`), so that the rules this change leaves as they are keep their source after the archive. It adds the item of D45 or D46 the change rests on among the decision numbers, and names last the section of this document that states it, for example `Source: D28 #10, #13; D29 (3); D46 (1); design.md, Decisions this change rests on; design.md, Decisions: D46 (1)`. The items are cited as `D45 (n)` and `D46 (n)`, with the numbers below; `design.md, Decisions: …` always names this document.

**Where the code is.** The command definitions and their schemas are in `packages/catalog/src`; the handlers, the write path and the limits in `packages/commands/src`; the pure rules (the state machine, the loop, flip and write limits) in `packages/core/src`; the tables in `packages/db/src/schema.ts` and `packages/db/migrations`; the generated contracts in `openapi/v1.json` and `packages/packet/schema/v1-beta.json`. Tests sit in each package's `test` folder. The MCP tool snapshot `mcp/tools.json` is empty: no tool is built yet. The `set_status` that the agent-surfaces capability describes is, today, the operation `requests.set_status`, `POST /api/v1/requests/{key}/status`, whose state `open` releases the claim; the delta on that capability describes no tool, only what the release does.

**Constraints.**
- The rules below are the code's, not new choices: a rule that would change the code is out of scope and becomes its own change.
- A MODIFIED requirement repeats its heading exactly and keeps every scenario it had.
- This change is archived after `add-tiehall-oss-v1`, whose requirements it modifies.

## Goals / Non-Goals

**Goals:**
- Every accepted item of D45 and D46 has one place in the specs that states it, concrete enough to test, and the tests that cover it are named.
- A reader of the specs learns the exact bounds, statuses, states and counts the code applies, without reading the code.

**Non-Goals:**
- Changing any behavior, status text or limit. Where a reading looks wrong, it is raised as an open question, not fixed here.
- Documenting code behavior outside D45 and D46, such as who may edit a message or the order of the members list beyond what the deltas need.

## Decisions

### Code-level additions the specs did not name (D45)

Accepted by the maintainer on 2026-09-27. Each item names a rule the code applies that no requirement of `add-tiehall-oss-v1` stated.

- **D45 (1). The packet `kind` and the request title.** A packet carries `kind` at its top level, `request` or `contract_change`; the contract section is required when the kind is `contract_change` and optional otherwise, and a revision keeps the request's kind (a change of kind gets 400). A request carries a title its requester writes, one line of 1 to 200 characters, returned under the request's `untrusted` object. *Why:* a discriminator lets the schema require the contract section for contract-change packets without a second schema, and a title gives inboxes, mirrors and pages a line to show that is not the need. *Alternatives:* deriving the kind from the presence of the contract section, which cannot tell a request with a hand-attached diff from a contract-change request; a title inside the packet, which would make a title change a packet revision. *Code:* `packages/catalog/src/packet.ts` (`PACKET_KINDS`, the discriminated union), `packages/catalog/src/requests.ts` (`requestTitle`), `packages/commands/src/packets.ts` (the kind check on a revision), `packages/db/src/schema.ts` (`requests.title`, check `requests_title_length`).
- **D45 (2). Field length limits.** Every text a person or an agent writes is bounded, and a value outside its bound fails the schema and gets 400. The bounds are: the request title, 1 to 200 characters after trimming, no control character; a message body, 1 to 65,536 characters, not all blank, no NUL character; in the packet, the need and the migration notes 1 to 20,000 characters, each acceptance criterion 1 to 2,000 with at most 100 of them, at most 100 code refs (repository 1 to 200, path 1 to 1,000, ref 1 to 255), at most 100 links (an http or https URL of at most 2,048 characters, a title of 1 to 200), the API name 1 to 200, a ref 1 to 255, a sha of 40 or 64 lower-case hex digits, the engine's name and version 1 to 100, at most 1,000 changes (id 1 to 200, operation 1 to 1,000), the provider PR's repository 1 to 200 and URL at most 2,048, `extensions` keys of at most 255 characters and 16 KB of JSON in all; a team name, 1 to 100 characters after trimming. A packet text field is never blank. *Why:* unbounded text is a storage and rendering hazard, and a bound in the schema is the same on every surface and in the published packet schema. *Alternatives:* bounds enforced only by the database, which would answer 500 instead of 400; one bound for everything, which is too small for a need and too large for a title. *Code:* `packages/catalog/src/requests.ts`, `messages.ts`, `packet.ts` and `teams.ts`; `packages/packet/schema/v1-beta.json` carries the packet bounds as `maxLength` and `maxItems`.
- **D45 (3). The `messages.get` and `members.list` operations.** `messages.get`, `GET /api/v1/messages/{messageId}` with the scope `requests:read`, returns one message with every version of its text, oldest first, and the request whose thread holds it (id, key and target team); every member may call it, and an id that names no message gets 404. `members.list` is an internal command, offered in the web UI to every member and on no agent surface: it lists the install's members, ordered by GitHub login, each with their login, kind, bot flag, role and the keys of their teams. *Why:* the thread returns only the latest version of each message, so a read that shows every version needs its own operation; the members page needs a list, and a list of members is not an admin action. *Alternatives:* versions inline in the thread, which makes every thread read carry every edit; an admin-only members list, which would hide from members who is on their team. *Code:* `packages/catalog/src/messages.ts` (`getMessage`), `packages/catalog/src/members.ts` (`listMembers`), `packages/commands/src/messages.ts`, `packages/commands/src/users.ts`.
- **D45 (4). The `request.state_changed` event.** A change of state that another change brings about appends its own domain event, `request.state_changed`, which names the request, the state it left and the state it is in now. It is written when a blocking question moves a request to `needs_info` and when the last answer returns it; when a decline, a withdrawal or a done proposal takes effect; when a confirmed reassignment returns the request to `open`; and when an undo restores an earlier state. A claim, the start of work and the release of a claim are recorded by their own events (`request.claimed`, `request.started`, `request.released`) and add no state-change event. *Why:* readers of the loop need to see a state change that no message event names by itself, and one event type keeps the reader simple. *Alternatives:* a state on every message event, which puts the same fact in two places; one event type per transition, which multiplies types. *Code:* `packages/core/src/event-types.ts` (`requestStateChanged`), written in `packages/commands/src/messages.ts`, `proposal-confirmations.ts` and `proposal-undo.ts`.
- **D45 (5). `orgs.setup_completed_at` and a nullable org name.** The install's one org row exists from the web role's first start, before anyone has named it: its name is null until the setup screen names it, and `setup_completed_at` is null until the first admin's sign-in completes setup. "Setup is complete" means that time is recorded. Until then the setup gate serves only `/setup`, `/healthz` and, once the App's credentials are stored, `/webhooks/github`, and every operation that reaches `execute()` answers 503 `setup-required` anyway, because the transaction wrapper reads the org row first. Once the gate has seen setup complete, it lets every call through without reading the row again. *Why:* the setup code needs a row to hang its hash on before the company has a name, and one time column says both that setup is complete and when. *Alternatives:* a separate settings row for setup state, which is a second row to keep in step; a name given in `.env`, which D36 keeps out of it. *Code:* `packages/db/migrations/0007_add_setup_completed_at.sql` and `0008_add_setup_codes.sql` (`ALTER TABLE orgs ALTER COLUMN name DROP NOT NULL`), `packages/commands/src/setup-code.ts` (`startSetup` makes the row), `setup-gate.ts`, `with-org.ts` (`SetupRequiredError`). The write of `setup_completed_at` itself comes with task 7.9 of `add-tiehall-oss-v1`; every test seeds it by SQL.
- **D45 (6). 412 for `If-Match: *`.** The REST route takes the revision a caller expects only from the `If-Match` header, as the strong entity tag of a revision, such as `"3"`; a field of the body is dropped, so a body that names a revision without the header still gets 428. A header that is not one strong entity tag of a revision, among them `*`, a weak tag such as `W/"3"`, a list of tags, an unquoted number, `"0"` and a word, matches no revision and is refused with 412 and the problem type `precondition-failed`, with the text that `If-Match` names no current revision; a strong tag of a revision that is no longer current gets the same status with the text that names the current revision. *Why:* adding a revision must name the revision it builds on, and `*`, which elsewhere matches any current representation, would let a writer skip that. *Alternatives:* treating `*` as "the current revision, whatever it is", which defeats the check; 400 for a malformed header, which hides that the precondition is what failed. *Code:* `packages/commands/src/rest.ts` (`revisionOfEtag`), `packages/commands/src/packets.ts`, `packages/core/src/error-model.ts` (`precondition-failed`, `if-match-required`).
- **D45 (7). Untimed setup sessions.** Entering the current setup code opens a setup session: a random 32-byte token in a cookie of that browser, stored as its hash, with no expiry. It stays valid until setup completes; once `setup_completed_at` is recorded, no session opens anything and `/setup` answers 404 to every browser. A later start prints a new code and replaces the stored hash, which stops the earlier code from opening new sessions, but it does not end the sessions opened with the earlier code. Entering the current code again opens another session. *Why:* setup is one sitting on a host the operator controls, and the setup code, not the clock, is what keeps strangers out; a session that expired mid-setup would make the operator read the log again for nothing. *Alternatives:* a session that expires after some minutes, which adds a clock rule with no threat it answers; ending every session at each start, which would make a restart during the manifest round trip lose the operator's place. *Code:* `packages/commands/src/setup-code.ts` (`openSetupSession`, `isSetupSession`), `packages/db/src/schema.ts` (`setupSessions`, which has no expiry column). Open Questions below asks whether a restart should end earlier sessions; the spec states what the code does.

### Readings the code chose where the specs were silent (D46)

Accepted by the maintainer on 2026-09-27. Each item is a reading the code took where a requirement of `add-tiehall-oss-v1` could be read two ways.

- **D46 (1). A release while `needs_info`.** Releasing a claim while the request is `needs_info` keeps it in `needs_info` with no claimant; once every blocking question has an answer, the unclaimed request returns to `open`, not to the state it had before the questions. A confirmed reassignment while the request waits does the same: it keeps `needs_info`, with no claimant, writes no state-change event, and the last answer returns the request to `open` in its new team. The state machine has one release rule, whatever calls it: a member of the target team releasing a departed claimant's claim, and `set_status` to `open`, which is how a release is called, keep a waiting request in `needs_info` the same way. Nobody can release a request blocked during triage, which nobody holds (409), and nobody can claim a request in `needs_info` (409). *Why:* the state a request returns to is about who holds it: `claimed` and `in_progress` say the claimant is working, and once nobody holds the claim, `open` is the only state that is true. *Alternatives:* returning the request to `open` at the release and dropping the questions, which would let it be claimed while its blocking questions wait; refusing the release while questions wait, which would lock a departing claimant in. *Code:* `packages/core/src/request-states.ts` (`release` and `answer_blocking`), `packages/commands/src/requests.ts` (`requests.set_status` with `open` is the one release path, for the claimant and for the target team once the claimant has left), `packages/commands/src/proposal-confirmations.ts` (a reassignment while waiting).
- **D46 (2). The team-pair cap counts each direction apart.** The cap of 50 agent-opened requests per pair of teams per UTC day counts an ordered pair: requests from BE to FE and requests from FE to BE are two pairs with two counts. The cap per user counts any 60-minute window, and both caps leave out requests people open in the web UI. *Why:* a loop between two teams' agents runs in one direction at a time, and the cap is meant to stop such loops without stopping the other team's own requests. *Alternatives:* one count for both directions, which lets one team's runaway loop exhaust the other team's allowance. *Code:* `packages/commands/src/write-limits.ts` (`capAgentOpenedRequest`, keyed by requesting and target team), `packages/core/src/write-limits.ts`.
- **D46 (3). Acknowledging counts toward no limit or budget.** Acknowledging events, which moves a read cursor, and reading count toward neither the per-token limit nor the daily budget nor any request's loop count, and are never refused by them; nor are writes recorded as `web_session`, `system` or `integration`, and a refused write is not counted whatever refused it. *Why:* an agent that cannot acknowledge cannot stop re-reading, and a limit that counted reads would make the loop itself trip it. *Alternatives:* counting every POST, which would count `events.acknowledge` because of its method. *Code:* `packages/commands/src/execute.ts` (the token write is counted inside `write()`, which the read and acknowledge handlers never call), `packages/commands/src/event-reads.ts`, `packages/commands/src/loop-limit.ts`.
- **D46 (4). Opening a request is not written to that request's loop count.** The loop count of a request starts with the first agent write on it after it exists; the opening itself is never counted, whoever opened it. The opening is still an agent write for the per-token limit and the daily budget, and counts toward the caps on agent-opened requests. *Why:* the loop limit counts the exchange on a request since a person last acted, and the request cannot have had a human action before it existed; the caps on opened requests cover loops that open requests. *Alternatives:* counting the opening as the first write, which makes every agent-opened request one write nearer the flag for no reason. *Code:* `packages/commands/src/requests.ts` (`requests.create` never calls `changesRequest`), `packages/commands/src/write.ts`.
- **D46 (5). A flip is counted when its blocking question is posted.** An agent's blocking question on a request that is `in_progress` records a counted flip on the UTC day it is posted, and the flip stays counted whether or not the round trip completes: the question may stay unanswered, the claim may be released, or the request may be reassigned, declined, withdrawn or done while it waits, and none of these uncounts it. A blocking question on a request that already waits in `needs_info` joins the round trip in progress and starts no new flip, and a question the limit posts as non-blocking records no flip. *Why:* the limit exists to stop an agent from bouncing a request, and the bounce is the question; counting only completed round trips would let a request be parked in `needs_info` without limit. *Alternatives:* counting at the answer, which counts the person who answers rather than the agent who asked; uncounting when a round trip breaks, which needs a rule for every way it can break. *Code:* `packages/core/src/flip-limit.ts` (`startsCountedFlip`), `packages/commands/src/messages.ts` (`countedFlipOn` is written at the post and never cleared), `packages/db/src/schema.ts` (`messages.counted_flip_on`).
- **D46 (6). The `needs_human` check comes after the side and state checks.** A write on a flagged request is refused for the flag only once everything else about it has passed. Those checks sit in several places, and the rule promises no order among them, only that the flag comes last: the REST route refuses a malformed `If-Match` (`*`, a weak tag, a list, an unquoted number, `"0"` or a word) with 412 before the input schema is checked; the schema (400) is checked next; the handler then looks up the request the key names (404), checks the caller's side (403) and the request's state (409 without the problem type `needs-human`), and, for a revision, refuses a missing `If-Match` (428), a stale strong tag (412) and a change of kind (400) after the side check; last, in the write's transaction, the per-token limit and the daily budget (429) are counted and the flag is checked. A write refused for any of these is not counted toward the loop, whether or not the request is flagged. *Why:* the flag says agents should stop writing on this request, not that the request's other rules stop applying; an agent that is not allowed to write learns that first, and a refusal never counts. *Alternatives:* checking the flag first, which would hide a 403 or a 409 behind `needs-human` and give an outsider the flag's state. *Code:* `packages/commands/src/request-changes.ts` (`assertSideAllows`, then `transition`), each handler in `packages/commands/src/requests.ts`, `messages.ts`, `packets.ts` and `proposals.ts`, which calls `changesRequest()` inside `write()` after those checks, `packages/commands/src/loop-limit.ts` (`countAgentWrite`).
- **D46 (7). Editing a message from a web session does not clear `needs_human`.** Only two things are human actions: a message posted from a web session and a confirmation in the web UI of a proposal on the request. An edit of a message from a web session adds its version, is neither counted nor refused, and leaves the flag and both counts as they are. An agent's edit is an agent write: counted, and refused while the request is flagged. *Why:* the flag asks a person to say something new on the request; rewording an earlier message is not that. *Alternatives:* treating any web write as a human action, which the specs already refuse for a claim or a state change made in the web UI. *Code:* `packages/commands/src/messages.ts` (`messages.post` calls `recordHumanAction` for a web session; `messages.edit` does not), `packages/commands/src/loop-limit.ts`.

No ADDED requirement is needed. `activity-log` needs no delta, because the state-change event is a domain event that the requests capability lists. `agent-surfaces` gets one delta, on the requirement that describes `set_status`: its sentence on a release said the request returns to `open`, which D46 (1) qualifies. Neither new read of D45 (3) is offered on an agent surface, and no MCP tool exists yet, so nothing else in that capability changes.

## Risks / Trade-offs

- [A spec that states the code's bounds and texts can drift when the code changes] → The tasks name the test for each item, and the CI checks of `add-tiehall-oss-v1` (the OpenAPI drift check and the packet-schema check) fail when a bound in the code changes without the committed contracts.
- [A rule stated here may be one the maintainer would rather change] → Each is marked as the code's reading with its alternatives; a change to any is its own OpenSpec change and touches only the requirement named in the table above.

## Migration Plan

None. Nothing is built, moved or migrated. The change is archived after `add-tiehall-oss-v1`, so its MODIFIED deltas apply to the requirements that change adds.

## Open Questions

- **A restart and earlier setup sessions (D45 (7)).** A later start's new code leaves the setup sessions opened with an earlier code valid. The spec states this as the code has it. If the maintainer wants a restart to end every setup session, that is a small code change and its own OpenSpec change.
- **`setup reopen` and setup sessions.** The operator command is not built yet (task 21 of `add-tiehall-oss-v1`). Whether reopening the App step opens a fresh setup session or accepts an earlier one is unstated; the specs of that command decide it when it is built.
- **The state a reassigned, waiting request returns to (D46 (1)).** The code returns it to `open` in its new team once its questions are answered, because nobody holds it. No decision text names the reassignment case; the spec states the code's reading.
