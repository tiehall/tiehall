# Tasks

One group, in milestone M1 "It works" of the main change, `add-tiehall-oss-v1`. D50 has the maintainer approve this change before its spec-changing parts are built. Tasks 1.1 to 1.11 cover the items where the code already does what the new rule says and the spec only catches up (D50 (1), (8), (9), (11)'s kept rules, (13), (14) and (18) to (22)): each names the tests that cover its rule and writes the ones that are missing, as plain tests, because the behavior exists; they change no behavior. Tasks 1.12 to 1.23 change code or the text of earlier changes, and wait for the maintainer's approval. Their order: the error model's new row (1.12) comes before the key check (1.13) and the invite form (1.16) that use it, one pending invite per account (1.15) before the review page that names the invite it replaces (1.16), and 1.12's page for a code GitHub did not convert before the renderer of 1.17 that negotiates it. Some cases extend main tasks that are not built yet, `setup reopen` (21.2), the install docs (21.9), the admin page's banners (21.10), PR links and close on merge (16.8, 23.x), the mirror's tracker "Done" (24.7), the broken-installation banner (24.11), Jira (25.1, 25.2), the error model's coverage check (26.7), the consent and device approval pages (group 15), request URLs, intake pages and the web app's pages (group 18) and the admin docs (28.6); those cases are written with those tasks, and where a main task's text differs from this change, this change's tasks govern. When a task renames a test that `tools/repo-checks/security-events.json` or `tools/repo-checks/confirmation-actions.json` names, it changes that file in the same commit, and `pnpm check:security-events` and `pnpm check:confirmations` still pass.

Tasks read as in the main change's tasks.md: the checkbox line is the whole task, with how it is verified and, in brackets, the requirements it implements; tests come first and are committed as expected failures (`it.fails` or `test.todo`) until the task that makes them pass.
