# Design: GitHub layer hardening

## Context

[proposal.md](proposal.md) says why the GitHub layer needs a hardening change. This document restates the decision the deltas rest on, D50, and each of its twenty-two items as a public rule with its reason and the alternatives that lost, numbered so that the maintainer can approve each one or change it. It then says how the items are built, which texts of earlier changes they correct, and what stays open. It cites nothing outside this repository.

**Where the items come from.** The GitHub layer was built by the main change's tasks 7.1 to 7.15 (setup and sign-in), 9.5 to 9.12 (invites and the admin pages) and group 10 (webhooks, installations, modes, polling, departures and the App key), and by `github-app-reachability`'s tasks 1.1 to 1.5 and 1.7 to 1.9. Its builders, its verifiers and the fixer who followed them left notes for the maintainer wherever the code had to choose something the specs did not say, or said differently. Items (1) to (17) each settle one such note, with the default the notes recommended. Items (18) to (22) record hardening that D50 had built directly, because it stays inside what the specs allow, but whose rule the specs do not state, or state otherwise; the specs catch up with them.

**Current state.** Built: the setup gate and setup code (7.1, 7.2), the GitHub stub (7.3), the manifest flow (7.4, reachability 1.2 to 1.4), with the manifest state's expiry and single use, the notice that names a replaced App and the bound on the App's name, the sign-in service and its admission, identity, email and events (7.6 to 7.15), with its rate limit, setup completion (7.9), invites and their revocation (9.5, 9.6), the admin pages (9.12), `/webhooks/github` (10.1), with its 25 MiB body limit, delivery processing (10.2), installations and covered repositories (10.3, 10.4, reachability 1.5), outbound calls (10.5), with the 10-second timeout on every GitHub request, redelivery (10.6), the mode and its check (10.7, reachability 1.7, 1.8), polling (10.8), organization departures (10.9), whose read of an account by its id the invite's review page reuses, and the rotated App key (10.10). Not built: `setup reopen` (21.2), the install docs (21.9), the admin page's integration state and banners (21.10), PR links and close on merge (16.8, 23.x), the GitHub Issues mirror and its tracker "Done" (24.x, 24.7), the broken-installation banner (24.11), Jira (group 25), the error model's coverage check (26.7), the consent and device approval pages (group 15), request URLs, intake pages and the web app's pages (group 18), and the user and admin docs (28.6).

**How the specs cite this document.** Every `Source:` line in `specs/*/spec.md` keeps the decision numbers its requirement cited before this change, adds the items of D50 it rests on, such as `D50 (4)`, and names the sections of this document: `design.md, Decisions this change rests on`, where D50 and its items are, and `design.md, Rules carried from earlier changes`, which says where the unchanged parts of each requirement keep their sources.

**Constraints.**
- A MODIFIED requirement repeats its heading exactly and keeps every scenario it had. Where `github-app-reachability`, `spec-catch-up` or `request-body-limit` already modify or add a requirement, this change starts from their text.
- No operation of `/api/v1` changes: no operation offered on REST calls GitHub during the call today, and HTML pages go only to browsers on the web UI's page routes. The OpenAPI document does not change.
- Nothing new calls a service other than GitHub (the main change's S13), and no new kind of GitHub call is added: the invite's review page and its confirmation read the account by its id with `GET /user/{account_id}`, which organization departures already make (`gitHubAccountWithId` in `packages/commands/src/github-users.ts`), and the key check moves from one App endpoint to another (D50 (2)).
- No call to GitHub is made inside a database transaction, as `execute()` already ensures for handlers with its step before the call's transaction (`execute.ts`); the review pages follow the same rule (T6).
- The spec-changing items wait for the maintainer's approval before they are built (D50).

## Goals / Non-Goals

**Goals:**
- Every note the GitHub layer's builders left for the maintainer is settled, in one place, with its reason and its alternatives, and every rule its hardening built is stated in the specs.
- The specs say what the built GitHub layer does, and where the recommended rule differs from the code, the tasks change the code, tests first.
- Each rule is concrete enough to test, and each task names the test that covers it or writes it.

**Non-Goals:**
- Hardening that stays inside what the specs already say, and says in them. D50 has it built directly, outside this change.
- The Jira connection check itself (the main change's group 25), the admin banners (21.10, 24.11) beyond the case D50 (15) adds, and the consent, device approval, request URL and intake pages beyond the case D50 (7) adds.
- The Jira webhook's body limit, which stays `request-body-limit`'s Open Question; D50 (19) settles only `/webhooks/github`.
- A rename of the company after setup, an erasure of refused sign-in records, and settings for any length of time named here (Open Questions).
- GitHub's answer to hook URLs on a private network, which `github-app-reachability`'s task 1.10 measures.

## Decisions

### Decisions this change rests on

- **D50. The GitHub layer's notes are settled by recommended defaults.** Taken by the maintainer on 2026-09-29. As public rules:
  - The technical notes that the builders, verifiers and fixer of the GitHub layer left for the maintainer are settled by the defaults the notes recommended.
  - Hardening that stays inside what the specs already say is built directly.
  - Points where the specs and the code disagree, or where a new rule is needed, go into this one change, `github-layer-hardening`, which lists each decision with its rationale and alternatives, and which the maintainer approves before its spec-changing parts are built.
  - **Why.** The notes are many and small, and each has a clear default; deciding them one at a time would stall the GitHub layer for no better result. Keeping the spec-changing ones in one change keeps the specs the contract: nothing the code does differs from them once this change is built.
  - **Alternatives that lost.** *One change per note:* twenty-two proposals for points that touch the same few requirements, which would modify each other's text. *Building every default at once, specs after:* the code would run ahead of the contract the maintainer approves.

Each item below states its rule, why it wins, the alternatives that lost, and whether the spec catches up with the code or the code changes; items (18) to (22) also say where the built code and its tests are. Its label in brackets names the note it settles or, for items (18) to (22), the hardening it records.

- **D50 (1). Tiehall calls GitHub only with its App's own credentials** [installation-token-wording]. *The spec catches up.*
  - **Rule.** Tiehall uses a JSON web token (JWT) of its App, signed with the App's private key and issued by its client id, for the App's own endpoints: listing the App's installations and reading one, requesting an installation token, reading the App (`GET /app`), reading the webhook delivery log and asking for a redelivery. It uses an installation token for everything done in an installation: reading pull requests, users, organization members and the repositories an installation covers, and writing issues, comments and labels. It uses the App's client id and client secret only to exchange the code of a sign-in in progress for that sign-in's user token. The exchange of the manifest's code during setup carries no credential. The only other token Tiehall ever sends to GitHub is the user token of a sign-in in progress: that sign-in uses it once to read who signed in (`GET /user`) and once to read their email addresses (`GET /user/emails`), and never stores it. A token a client presented to Tiehall is never used or forwarded.
  - **Why.** GitHub requires the App's JWT on the App's own endpoints and takes no installation token there; it issues a sign-in's user token only for the App's client id and secret; the manifest conversion is unauthenticated by GitHub's design; and the sign-in capability's first sentence already says that sign-in reads who signed in. The code does exactly this, and `packages/commands/test/github-outbound-calls.test.ts` asserts it; only the specs' "every call with installation tokens" is inexact, in four requirements, in the main change's S4 and in its tasks 7.7 and 10.5.
  - **Alternatives.** *Keeping "installation tokens only" and naming exceptions in each requirement:* four requirements that a correct build contradicts. *Reading who signed in with an installation token:* GitHub gives a person's email addresses only to the token that person authorized.
- **D50 (2). An uploaded App key is checked with `GET /app`** [key-check-get-app]. *The code and the spec change.*
  - **Rule.** Tiehall checks an uploaded private key by asking GitHub for the App itself, `GET /app`, with a JWT signed with the new key whose issuer is the stored client id, and accepts it only when GitHub answers 200 with the stored App id. A 401 means GitHub does not accept the key, as for a key of another App or one deleted on GitHub: the upload gets 400, nothing is stored and the key in use stays. The check needs no installation and uses none, so an upload works while no installation is connected. A failure or no answer is D50 (3)'s 502.
  - **Why.** `GET /app` proves exactly what matters: that the key signs for this App and that GitHub holds it as active. Today the code requests an installation token through a connected installation, and answers 409 when none is connected, because an installation no admin connected is only listed; so an admin who must replace a leaked key right after a setup that connected nothing cannot.
  - **Alternatives.** *An installation token through any installation, connected or not, as S4 and the requirement word it:* uses an installation no admin connected, against the tracker-mirrors rule that such an installation is only listed. *The installation token and the 409, as built:* no key can be replaced while nothing is connected. *No check:* a wrong file would break every call to GitHub until someone noticed.
- **D50 (3). GitHub or Jira unavailable is 502 `integration-unavailable`** [github-unavailable-502]. *The code and the spec change.*
  - **Rule.** The error model gains a row: GitHub or the Jira site failed a call that the action needs, by answering with an error the action gives no answer of its own for (a 5xx, a rate-limit refusal, a refused manifest code), or by not answering within 10 seconds, the time every GitHub request already waits → 502 with the problem type `integration-unavailable`. Nothing changes, and a confirmation the action carried stays unused, so the admin can confirm the same review page again while it is valid. The row serves the invite form's look-up of a username, the review page's and the confirmation's read of the account (D50 (12)), the key check (D50 (2)), the setup screen's exchange of the manifest's code, which already answers 502 with a page, and, when the main change's group 25 builds it, the check of the Jira connection. An answer the action does define keeps its own meaning: GitHub's 404 to the look-up is Tiehall's 404 for no such account, and GitHub's 401 to the key check is Tiehall's 400 for a key GitHub refuses. A manifest code that is missing, or not in the form GitHub issues codes in, is Tiehall's own 400 for input that fails the schema, and GitHub is not asked.
  - **Why.** A 500 tells the admin that Tiehall is broken when the cause is outside it, and says nothing about trying again. One row keeps every surface consistent, and the main change's task 26.7 can hold it to a test like every other row. A malformed code is the request's fault, not GitHub's.
  - **Alternatives.** *503:* says that Tiehall itself is unavailable. *502 for errors and 504 for timeouts:* two rows for one cause that the admin handles the same way. *500, as built for the look-up and the key check:* the cause is hidden.
- **D50 (4). Deliveries are kept 7 days after they are processed** [delivery-retention]. *The code and the spec change.*
  - **Rule.** Tiehall deletes a stored GitHub delivery, its payload included, 7 days after it was processed. A delivery not processed yet, because it is held until setup completes or its job failed and waits in the dead-letter queue, is kept until it is processed, and at most 30 days after it arrived, whether or not setup has completed; one held before setup is processed when setup completes only if Tiehall still holds it. The rule covers every row the processing reads, the changes the poll of polling mode stores in the same form included. A nightly pruning job does the deletion, beside the pruning of IP addresses and user agents that the main change's T6 lists among the crons, and runs before setup completes too.
  - **Why.** Payloads carry the text of PRs and issues and people's details that Tiehall does not need once processed. 7 days is longer than GitHub's 3-day redelivery window, so a redelivered id is still recognized and processed once; and processing reads the state of what changed rather than replaying the delivery's action (the main change's T16 makes Tiehall's jobs level-triggered), so a delivery that arrives again after its row is gone changes nothing more. 30 days bounds what a stalled setup or a neglected dead-letter queue keeps.
  - **Alternatives.** *Forever, as built:* the install keeps every payload for no use. *Deleting at once when processed:* a redelivery within GitHub's window would be processed again. *Keeping the ids and dropping only the payloads:* one more rule for little gain over 7 days.
- **D50 (5). A refused sign-in's record lasts as long as its event** [refused-sign-in-retention]. *The code and the spec change.*
  - **Rule.** The record of a refused sign-in (the `sign_in_refusals` table) holds only the GitHub account's numeric id, the login it had and the time of the refusal, and is kept as long as the security event that names it: the activity log is append-only, and the event must name the refused account. The admin view of the activity log shows the refused account's login and numeric id beside the event, before and after the 90 days. The refusal's IP address and user agent follow the 90-day rule of every security event. Deleting such records is part of the main change's Open Question on erasure.
  - **Why.** The event is the record admins need to see who tried to get in. An account's numeric id and login are public on GitHub, and nothing private is kept past 90 days. The record is written and kept as the rule says today, but no reader of it exists: the admin view prints only the record's id, so it learns to show the account.
  - **Alternatives.** *Deleting the record with the IP address after 90 days:* the event would name a record that no longer exists, and the admin view could no longer say whose sign-in was refused. *The account inside the event:* events carry ids, never content (the main change's T5).
- **D50 (6). A web session lasts 7 days from its last extension, and 30 days at most** [session-lifetime]. *The code and the spec change.*
  - **Rule.** A web session expires 7 days after it was created or last extended. A use extends it to 7 days after that use when a day or more has passed since it was created or last extended, so a session in use expires between 6 and 7 days after its last use. It ends at the latest 30 days after the sign-in that created it; the browser is then sent to sign in, not refused as a removed member's, and the person signs in with GitHub again, which runs the admission check, the organization departure check and the read of their email address again. Signing out and a removal still end a session at once. The session that the setup screen's sign-in creates follows the same rules.
  - **Why.** Today a session lasts the sign-in library's default of 7 days from sign-in and is never extended, because Tiehall reads sessions with the library's refresh turned off; so a person who uses Tiehall every day is signed out every week. The 30-day cap bounds what a stolen cookie is worth and makes everyone pass the sign-in checks at least monthly. The confirmation step and the membership re-check on every call keep the risk of a live session low.
  - **Alternatives.** *7 days from sign-in, as built:* a weekly sign-in for daily users. *A sliding window with no cap:* a session could live for ever and never meet the sign-in checks again. *A fixed 30 days:* a lost laptop's session stays valid for a month even when nobody uses it. *A setting:* every operator would have to choose, for no gain in v1.
- **D50 (7). Refusals to browsers are pages** [html-refusals-for-browsers]. *The code and the spec change.*
  - **Rule.** On the routes that serve the web UI's pages (the web UI's pages and their forms, the setup screen, the review pages and confirmations under `/confirm/…`, the consent and device approval pages, and request URLs and intake pages when they answer in HTML) and on GitHub's return to either sign-in callback, a refusal to a request that negotiates HTML is an HTML page. On request URLs and intake pages, a request negotiates HTML exactly as the agent-surfaces capability defines; on every other of these routes, when its `Accept` header names `text/html`, as browsers send. The page has the refusal's status, the problem's title and detail in Tiehall's own words, and a way on: back to the page whose form was refused, to the page that was asked for, or to `/sign-in` for a refused sign-in or a browser that is not signed in. Every other request to those routes, and every call to `/api/v1`, `/mcp` and every other route, still gets `application/problem+json`. The error model's sentence "as an RFC 9457 problem details object" allows this one exception, and a scenario elsewhere that names a problem means this page for a browser on these routes. The setup gate's answers before setup completes are unchanged.
  - **Why.** Statuses and problem types stay the same for tests and tools, and a person told to ask for an invite, or refused an admin page, sees a page they can act on, not JSON.
  - **Alternatives.** *Problem JSON everywhere, as built:* right for tools, unreadable for people. *A page on these routes whatever the client asks for:* a test or a script that asks for JSON gets HTML. *A redirect to an error page:* loses the status.
- **D50 (8). The setup screen keeps its own sign-in callback** [setup-sign-in-callback]. *The spec catches up.*
  - **Rule.** The manifest carries two sign-in callback URLs on `TIEHALL_URL`: the sign-in's, `/api/auth/callback/github`, and the setup screen's, `/setup/sign-in/callback/github`. The setup screen's sign-in, a second instance of the sign-in service under `/setup/sign-in`, completes setup, or closes a step that `setup reopen` opened, and is served only while setup, or such a step, is open. The setup gate's rule stays as written: before setup completes, only `/setup`, `/healthz` and, once the App's credentials are stored, `/webhooks/github` are served, so `/api/auth` answers as every API call does then. The install docs (the main change's task 21.9) name both URLs for an operator who moves the install to a new host (the main change's S15) and must change the App's URLs on GitHub.
  - **Why.** The surface a host exposes before it has an admin stays `/setup` alone.
  - **Alternatives.** *One callback under `/api/auth`, served before setup to a browser with a setup session:* widens what a host with no admin yet serves, and mixes the setup sign-in's rules (no admission check, a first admin) into the usual sign-in. *The usual sign-in under `/setup` too:* `/setup` answers 404 once setup completes.
- **D50 (9). The company's name is bounded and set only during setup** [company-name-bounds]. *The spec catches up.*
  - **Rule.** Bounded as D45 (2) bounds a team's name, 1 to 100 characters after leading and trailing blanks are removed, and, as D45 (2) bounds a request's title, with no control character; the setup screen refuses any other name with 400 and changes nothing. The operator can change the name on the setup screen until setup completes. v1 offers no way to rename the company after setup; a rename by an admin, with the confirmation step and as a security event, is an Open Question.
  - **Why.** Every text a person writes is bounded in the specs, and a company's rename is too rare to be worth v1's scope.
  - **Alternatives.** *A rename by an admin in v1:* a page, a review page and a security event for a rare action. *A rename through `setup reopen`:* that command reopens only the App step.
- **D50 (10). An integration event acts only for a member** [integration-event-non-member]. *The code and the spec change.*
  - **Rule.** An integration event acts for the Tiehall user of the account that the webhook names as the one that made the change (a delivery's sender, or a linked Atlassian account) only while that user is a member of the install when the event's command runs. For anyone else, removed or never admitted, and for an account that maps to no user, it acts for no user and is recorded with the actor kind `integration` and no user, like an unmapped account. A change the poll of GitHub reads acts for the user of the account that GitHub's read names as having made it, where it names one, such as the `closed_by` of a closed issue, while that user is a member, and for no user otherwise (decisions-from-groups-15-28, D55 (77)). So a removed person's GitHub activity, such as a tracker "Done" or a merged PR, never produces a proposal or an action in their name.
  - **Why.** Every call made for a user re-checks that the user is a member (the main change's Design rules: Teams and roles), and D28 #75 already falls back to the provider team for a PR author who is not a member. Today the processor maps the sender to their user whether or not they are a member, and the integration caller skips the membership re-check, so a check in the mapping alone would still act for a person removed between the mapping and the command.
  - **Alternatives.** *Acting for the mapped user, as built:* a removed person's user appears as the one new changes act for. *Refusing the event:* the change itself is lost, though a merge still closes a request as a system action. *Reading the author of a polled change from the pull request:* the author of a pull request is not the one who made each change to it.
- **D50 (11). The invite rules as built, and one pending invite per account** [invite-edge-rules]. *The spec catches up, and one rule changes the code.*
  - **Rule.** Kept as built: an invite for an account whose person is already a member gets 409, now on the invite form (D50 (12)); a login that names a GitHub organization gets 404, because it names no person's account, as the main change's R9 reads a login that names no account; revoking an invite that a sign-in accepted gets 409; revoking one that is already revoked changes nothing more and records nothing more; with no connected installation to look the login up through, the invite gets 409. Changed: a new invite for an account that has a pending invite (neither accepted, revoked nor expired) replaces it: the older invite is revoked in the same write, `invite.created` and `invite.revoked` are both recorded, and the review page says which invite, with its role and when it expires, the new one replaces.
  - **Why.** Every refusal becomes testable from the spec. One pending invite per account removes the question of which role wins, instead of answering it by age as the sign-in does today (the newest valid invite), and the invites page never lists two invites for one person.
  - **Alternatives.** *Several pending invites, the newest winning, as built:* two invites with different roles wait side by side. *Refusing a second invite with 409 until the first is revoked:* one more step for an admin who only wants to change the role. *Keeping the older invite:* the admin's latest choice would be lost.
- **D50 (12). The invite form resolves the account before the review page** [invite-review-resolves-account]. *The code and the spec change.*
  - **Rule.** Tiehall resolves the username when the invite form is submitted, before any review page, with a read through a connected installation's token. A login that names no person's account gets 404 on the form, and an account whose person is already a member gets 409 there, each with no review page. Otherwise the review page names the account in Tiehall's own words by its login, its numeric id and the date it was created, and shows the display name GitHub gives as content Tiehall did not generate, fenced as data with the origin external and escaped, because anyone can set a display name. The review page and the confirmation read the account by its id, outside any transaction; a read that fails or does not answer within 10 seconds is D50 (3)'s 502. The action's input carries the numeric id and the role, so the confirmation's digest binds the invite to the account the admin saw.
  - **Why.** The main change's S7 says the review page shows exactly what will happen, and fences text Tiehall did not write. An invite admits a person, and a typo that names a stranger's real account should be seen before the confirmation, not after.
  - **Alternatives.** *Resolving at the confirmation, as built:* the admin confirms without seeing which account the login names, and a typo's 404 comes only after the confirmation. *Resolving on the review page with the login in the input:* the digest binds the login, and a rename between the review and the confirmation could bind another account. *The display name in Tiehall's own words:* text anyone can set would read as Tiehall's.
- **D50 (13). The bounds of a webhook secret, a private key and a review page's file** [secret-and-key-input-bounds]. *The spec catches up.*
  - **Rule.** As D45 (2) records the others: a webhook secret has 1 to 1,024 characters; a private key has at most 16,384 characters in PEM form (GitHub issues 2,048-bit RSA keys of about 1.7 KB); a file picked on a review page has at most 64 KB (65,536 bytes). A value outside a bound gets 400 and stores nothing. All three are far below the 2 MiB limit on form bodies that `request-body-limit` sets.
  - **Why.** Every input is bounded in the spec, so its 400s are testable and stable.
  - **Alternatives.** *No bound in the spec:* the code's bound could change silently. *The 2 MiB body limit alone:* a pasted value could fill a secret column with megabytes.
- **D50 (14). The admin pages' reads** [admin-reads-and-pages]. *The spec catches up.*
  - **Rule.** `invites.list`, `teams.list` and `settings.get_sign_in_policy` are internal, admin-only commands, offered on no agent surface: reading the pending invites, the teams with their earlier keys and people, and the sign-in policy is part of managing them (D28 #4), as D45 (3) recorded `members.list`. D50 (12)'s look-up of the account a username names is one more such read. The page paths stay out of the specs, under the main change's "Where the specs leave room: The admin UI's layout", and are listed here so that the docs (the main change's task 28.6) can name them: `/members`, `/admin/invites`, `/admin/teams`, `/admin/sign-in-policy` and `/admin/github`.
  - **Why.** The same treatment D45 (3) gave `members.list`, while the paths stay free to change.
  - **Alternatives.** *Page paths in the specs:* a layout change would become a spec change. *The reads unnamed:* the spec's admin list would not say that a member cannot read the invites.
- **D50 (15). Redelivery's limits, and a fallback to polling** [redelivery-limits-fallback]. *The parameters stay as built; the fallback changes the code and the spec.*
  - **Rule.** Design parameters, as built: Tiehall asks GitHub to redeliver each failed delivery at most 5 times; a run reads the delivery log back at most 3 days, GitHub's redelivery window, and from 15 minutes before its previous run. New rule: when a delivery made after the App's credentials were stored is still failed after Tiehall's last request to redeliver it, the delivery is given up, and Tiehall records the give-up. A banner about GitHub's webhook then shows, as D28 #83 has every integration banner show, to the admins and to the members of each team whose mirrors go through GitHub, until an admin next switches GitHub's mode or a delivery that reaches the install after the give-up is verified; every admin gets one email about it when SMTP is set, however many deliveries are given up while the banner shows. And GitHub moves to polling mode, as the check after the first installation would move it, unless the latest change of the mode was an admin's switch to webhook mode for the App in use, which Tiehall does not undo. Tiehall's switch is a security event for a changed integration that names no user, with the cause "a given-up delivery".
  - **Why.** Without it, a webhook path that breaks after the first check silently loses changes, and with them close on merge. The fallback reuses S9's own rule. The banner clears when the webhook works again, so an admin who kept webhook mode need not switch the mode twice to clear it. It settles part of `github-app-reachability`'s Open Question on the delivery log after webhook mode is chosen: Tiehall watches the log through redelivery in every webhook mode, alerts on a given-up delivery, and switches on its own only when no admin chose webhook mode.
  - **Alternatives.** *Asking for ever:* a delivery that can never succeed costs calls every run and hides the breakage. *An alert and no switch:* the install loses changes until an admin acts. *A switch even after an admin's choice:* overrides an admin who may be fixing the webhook at that moment. *A banner for admins only:* the members whose mirrors wait on GitHub would not know why, against D28 #83. *An email for each given-up delivery:* one breakage would flood every admin's inbox.
- **D50 (16). The earlier changes' texts match the code** [design-text-corrections]. *Text only.*
  - **Rule.** This change records that the main change's task 10.10 settled `github-app-reachability`'s Open Question "A rotated key in the review page's URL": the key travels only in the body of the review page's form, never in its URL or its input. That Open Question is removed from `github-app-reachability`'s design.md, which is not archived yet. The main change's T7 "Changed" paragraph and task 7.7 name the pair of hooks that clears the user token, `databaseHooks.account.create.before` and `account.update.before`, as T7's own spike correction and the code do, not an after-hook; and 7.7's "accepts only installation tokens" reads as D50 (1) says. The section "Text corrections to earlier changes" below lists every edit, these and the ones D50 (1), (2), (4), (11), (12), (15), (17) and (19) need.
  - **Why.** The design is the source of truth, and it must match the code that is built.
  - **Alternatives.** *Leaving the old texts, since this change supersedes them:* a reader of the earlier change would find rules that are no longer true.
- **D50 (17). The App's default name comes from the company** [default-app-name]. *The code and the spec change.*
  - **Rule.** The App's default name is "Tiehall", a space and the company's name that the setup screen's previous step recorded, cut to 34 characters, the longest name GitHub accepts for an App, with any trailing blank, dot or hyphen removed, as the default made from the host already is. The operator can still edit it. Before its button, the App step also says that GitHub may refuse the name as taken, and that the operator can then change it on GitHub's own page, which keeps the name editable beside GitHub's message, or come back to `TIEHALL_URL/setup` in the same browser and change it there, the same way back as for a refused webhook URL.
  - **Why.** App names are unique across GitHub, so the default "Tiehall localhost" of every trial install is taken after the first trial anywhere, and every later trial operator must edit it. The App's slug, and the bot name on every mirror issue and comment, then reads like `tiehall-acme[bot]` rather than `tiehall-tiehall-acme-com[bot]`. Removing a trailing dot or hyphen keeps the rule the built default has, which a cut in the middle of a name needs.
  - **Alternatives.** *The host, as built:* unique for real hosts but long, and always taken for `localhost`. *A random suffix:* unique, but means nothing to the people who read the bot's name. *Removing only trailing blanks:* a cut name could end in a hyphen, and the rule would differ from the one built for no gain.
- **D50 (18). The manifest's state expires after 60 minutes and is used once** [manifest-state-expiry]. *The spec catches up.*
  - **Rule.** Besides a `state` that is missing or not bound to the current setup session, the setup screen refuses with 403, before GitHub is asked and storing nothing, a return whose `state` was issued more than 60 minutes before, or whose `state` already brought back an App's credentials.
  - **Why.** GitHub converts a manifest code only within an hour of issuing it, so an older state serves no honest return; and a state that brought back one App brings back no other, so a return replayed from a browser's history asks GitHub nothing and changes nothing.
  - **Alternatives.** *No expiry, as first built:* a state leaked from a browser's history stays usable as long as the setup session, which has no expiry. *An expiry without single use:* a return replayed within the hour would ask GitHub again.
  - **Code.** `packages/commands/src/setup-github.ts` and `setup-route.ts`, with the used states on the setup session's row; tested in `packages/commands/test/setup-github-app.test.ts`.
- **D50 (19). A GitHub delivery's body is limited to 25 MiB** [webhook-body-limit]. *The spec catches up.*
  - **Rule.** `/webhooks/github` refuses a body larger than 25 MiB (26,214,400 bytes) with 413 and the problem type `payload-too-large`, as `request-body-limit` refuses other bodies over their limit: before the signature is checked and before the body is read past the limit, storing nothing. A body of 25 MiB or less is not refused for its size, and the 2 MiB limit of other routes does not apply. This settles `request-body-limit`'s Open Question "Webhook deliveries" for `/webhooks/github`; the Jira webhook's limit stays open there.
  - **Why.** GitHub caps a delivery at 25 MB, which 25 MiB covers under either reading of MB, so no delivery GitHub sends is refused, while a sender without the secret can no longer make the install read an unbounded body before the signature check refuses it.
  - **Alternatives.** *No limit, as `request-body-limit`'s R1 reads:* any sender can make the install hold an unbounded body in memory. *2 MiB, like every other route:* a delivery GitHub may send, up to its 25 MB, would be refused and lost.
  - **Code.** `packages/commands/src/body-limit.ts` (`WEBHOOK_BODY_LIMITS`), `github-webhooks.ts`, the web role's request guard and the web app's proxy setting; tested in `packages/commands/test/github-webhooks.test.ts`, `packages/commands/test/bounded-body.test.ts`, `apps/server/test/web-role.test.ts` and `apps/web/test/next-config.test.ts`.
- **D50 (20). The sign-in callback has a rate limit** [sign-in-rate-limit]. *The spec catches up.*
  - **Rule.** GitHub's return to the sign-in callback, `/api/auth/callback/github`, the one route of the sign-in service served over HTTP, takes at most 100 calls from one client address in 10 seconds, in every environment the install runs in; the next call gets 429 with the problem type `rate-limited` and a `Retry-After` header, the error model's row for a limit, and creates no session. The client address is the one the web role's request guard puts alone in `X-Forwarded-For` (the main change's T7).
  - **Why.** The callback writes to the database and calls GitHub for anyone who reaches it, before any account is known; the library's own limiter was on only when `NODE_ENV` is production, so the limit depended on how the install was started.
  - **Alternatives.** *The library's default, on in production only, as first built:* a test or a differently started install runs with none. *A limit per user:* a sign-in has no user until it completes.
  - **Code.** `packages/commands/src/sign-in.ts` (`RATE_LIMIT_MAX`, `RATE_LIMIT_WINDOW_SECONDS`); tested in `packages/commands/test/sign-in.test.ts` and `apps/server/test/sign-in-rate-limit.test.ts`.
- **D50 (21). A replaced App is named on the setup screen** [replaced-app-notice]. *The spec catches up.*
  - **Rule.** While setup is not complete, a later return from the manifest flow that brings back another App's credentials, such as one from an App step opened earlier in another tab, replaces the stored App; the setup screen's next step then names each App it replaced, says that it is still registered on GitHub with a private key that nobody uses, and links to its settings on GitHub, where the operator can delete it.
  - **Why.** Every App the manifest flow creates stays registered on GitHub with a live private key; without the notice, nobody would know that the replaced one exists.
  - **Alternatives.** *Refusing the later return:* the App the operator made last, whose install step they are on, would be lost. *Replacing silently, as the specs allowed:* a live key stays on GitHub that nobody knows of.
  - **Code.** `packages/commands/src/setup-github.ts` and `github-app.ts`, with the replaced Apps in their own table; tested in `packages/commands/test/setup-github-app.test.ts`.
- **D50 (22). A name the operator gives the App is bounded** [app-name-bounds]. *The spec catches up.*
  - **Rule.** A name the operator gives the App has 1 to 34 characters after leading and trailing blanks are removed, the lengths GitHub accepts; for any other name, the App step says so and offers no button that creates the App.
  - **Why.** GitHub refuses a longer name on its own page, which leads nowhere back to the setup screen, so a manifest with one is a dead end.
  - **Alternatives.** *The field's `maxlength` alone, as first built:* a browser that ignores it posts a manifest GitHub refuses. *Cutting the name silently:* the App gets a name the operator did not choose.
  - **Code.** `packages/commands/src/setup-github.ts` (`APP_NAME_MAX_LENGTH` in `github-manifest.ts`); tested in `packages/commands/test/setup-github-app.test.ts`.

### Technical decisions

#### T1. The key check calls `GET /app`

- **Choice.** The GitHub client module (`packages/commands/src/github-client.ts`) replaces `requestInstallationToken`, its export from `packages/commands/src/index.ts` and its use in `install-github.ts` with a check that builds an App JWT from the uploaded key and the stored client id, calls `GET /app`, and answers accepted for 200 with the stored App id, refused for 401 or another App id, and throws the unavailable error of T2 for anything else or no answer within the client's 10 seconds. `InstallGitHub.checkKey` takes the credentials and the expected App id, and no installation id, here and in the test install of `packages/commands/test/support/install.ts`; `packages/commands/src/github-app-key.ts` no longer looks for a connected installation, so its 409 for none goes. The check still runs in the handler's step before the call's transaction. The stub answers `GET /app` for an App JWT and can delete an App's key (`deletePrivateKey`) already. The tests that hold the key check open to prove that no lock and no transaction is held (`heldTokens()` in `packages/commands/test/github-private-key.test.ts`) hold `GET /app` in place of the token request.
- **Why.** One App endpoint proves the key, with no installation in the loop.
- **Alternatives.** Reading `/app/installations` with the new key, which proves the same but lists data the check does not need.

#### T2. One unavailable error, one row

- **Choice.** `packages/core/src/error-model.ts` gains the row `integration-unavailable` (status 502, title "Integration unavailable", no `Retry-After`). Every GitHub request already gives up after 10 seconds (`GITHUB_REQUEST_TIMEOUT_MS` in the GitHub client module, the main change's task 10.5), an option that tests lower. The client module gains a loggable `GitHubUnavailableError`, thrown when GitHub answers with a status its caller does not handle, or not at all; `invites.ts`, `github-app-key.ts` and `setup-route.ts` turn it into the refusal. A handler that asks GitHub does so in its step before the call's transaction, where `execute()` checks the confirmation nonce without consuming it (`execute.ts`), so a refusal there leaves the nonce unused, as the row requires. A manifest code that is not in GitHub's form, which `convertManifestCode` refuses without asking GitHub, gets 400 `invalid-input` as a missing code does. The setup screen's answer to a code GitHub did not convert stays an HTML page, now naming the problem type in its markup, until T5's renderer answers it by negotiation. No operation offered on REST calls GitHub during the call today, so the OpenAPI document does not change; an operation that will, such as linking a PR (the main change's 16.8), gets the row, and 502 in its document, when it is built. The Jira connection check (25.1, 25.2) uses the same row for the Jira site.
- **Why.** One error type keeps the three callers alike, and the row keeps REST, MCP and the web UI alike.
- **Alternatives.** Each caller catching Octokit's errors itself, which drifts.

#### T3. The nightly pruning of deliveries

- **Choice.** A daily worker job beside `activity_log.prune_origins` deletes, in batches, the `github_deliveries` rows processed more than 7 days ago and the rows never processed that arrived more than 30 days ago, by the worker's clock; `github_redeliveries` keeps its own pruning. The job reads the install's one org row directly, as `/webhooks/github` does when it stores a delivery, and not through `withOrg`, which refuses to run before setup completes, because deliveries are held from the moment the App's credentials are stored.
- **Why.** The same shape as the pruning of IP addresses, which operators already see in the worker.
- **Alternatives.** Deleting in the processing job, which cannot keep a row the 7 days that dedupe needs, and never sees a delivery held before setup.

#### T4. Web session lengths

- **Choice.** The sign-in service is built with a session expiry of 7 days and an update age of 1 day. `session()` in `packages/commands/src/sign-in.ts` stops passing `disableRefresh`, and every route handler and server action that reads the session passes the renewed cookie the service returns on to its answer. The 30-day cap is Tiehall's own check, because the library has none: `session()` deletes a session created 30 days ago or more and reads it as none, so the browser is sent to sign in. It does not mark the session ended, because `session()` reads an ended session as a removed member's and answers 403. Server components cannot set cookies: `webCommands` (`packages/commands/src/web.ts`) reads the session for them without renewing it. Every page built so far is a route handler; a page that the main change's group 18 builds as a server component renews the session through the proxy (`apps/web/proxy.ts`), which runs before every route and can set the cookie, or through a route handler, and its tests include the renewed cookie.
- **Why.** The library's own refresh gives the idle rule; one check in `session()` gives the cap for every route.
- **Alternatives.** A job that deletes old sessions, which leaves a gap of up to a run between the cap and its effect.

#### T5. One renderer for refusals on page routes

- **Choice.** `packages/commands/src/html.ts` gains one function that answers a refusal for a request: a page when the request negotiates HTML, the problem otherwise. The page carries the page headers (no script, nothing loaded from another host, no framing; the install's stylesheet and icons, `web-ui-design`, D57 (9)), the refusal's status, its title and detail escaped, the problem type in its markup, and the link on. `web-pages.ts`, `admin-pages.ts`, `github-admin-route.ts`, `confirm-route.ts`, `setup-route.ts`, `activity-log-route.ts`, `home-route.ts`, `apps/server/src/request-guard.ts`, `page-routes.ts` and the sign-in service's answers in `sign-in.ts` use it; the consent, device approval, request URL and intake pages use it when they are built.
- **Why.** One place decides the negotiation and escapes the text, as one place renders every page today.
- **Alternatives.** A page per route, which drifts.

#### T6. The invite form, the account read and one pending invite

- **Choice.** An internal, admin-only read resolves a username to an account through a connected installation's token (`GET /users/{username}`, as today). The invites page's form runs it and, on success, sends the admin to the review page of `invites.create`, whose input becomes the account's numeric id and the role. The review page and the handler read the account by its id with `gitHubAccountWithId` (`packages/commands/src/github-users.ts`, `GET /user/{account_id}`, which the stub already answers with `name` and `created_at`), extended to return the display name and the creation date. Reviews run inside a read-only transaction (`confirmation-step.ts`), so review handlers gain a step that runs before that transaction, as `definePreparedHandler` gives execution one (`execute.ts`), and the review page's read happens there. The review shows the login, the id and the date as its own lines and the display name as a quote with the origin `external` (`quotePreamble` in `packages/core/src/confirmation.ts`). The handler reads the account again in its step before the call's transaction, then takes a transaction-scoped advisory lock keyed by the account id, refuses with 409 when the account's person became a member meanwhile, revokes the account's pending invite, if any, with its event, and inserts the new invite with its event, in one write. `tools/repo-checks/confirmation-actions.json`'s input for "creating an invite" becomes the account id in the same commit.
- **Why.** The id in the input is what the confirmation's digest binds. A lock on the account serializes two admins inviting one person at once, which a row lock cannot do when no row exists yet. No read of GitHub holds a transaction open.
- **Alternatives.** A unique index on pending invites per account, which cannot say "not expired" in a predicate. Reading the account inside the review's transaction, which would hold a connection open while GitHub answers.

#### T7. Integration events and membership

- **Choice.** Delivery processing (`packages/commands/src/github-delivery-processing.ts`) maps the sender to a user only when that user holds a membership of the install, through one helper beside `userOfGitHubAccount` in `github-users.ts`; `userOfGitHubAccount` keeps meaning identity. Because a member can be removed between the mapping and the command, `execute()` checks again, in the call's transaction, that the user an integration-event caller acts for is a member, and runs the call for no user when they are not, rather than refusing it. The poll's stored changes carry no sender, so they act for no user; group 25 applies the same helper to a linked Atlassian account.
- **Why.** One helper, before any processor runs, so the PR and tracker processors of 23.x and 24.x inherit the rule, and one check in `execute()` closes the gap for all of them.
- **Alternatives.** A check in each processor, which a later processor could forget. Refusing the call of a removed member's event, which would lose the change.

#### T8. Giving up a delivery

- **Choice.** The redelivery job (`packages/commands/src/github-redelivery.ts`) gives a delivery up when it has asked for it 5 times and the log's latest attempt still failed while Tiehall holds no such delivery. In the same write it sets `github_app.webhook_given_up_at`, when it is not set yet, and, unless an admin's switch to webhook mode was the latest change of the mode, sets polling mode with a `github.mode_changed` event whose cause is the new value `given_up_delivery` (`packages/core/src/event-types.ts`). One migration adds `webhook_given_up_at` and `mode_set_by` to `github_app` and `given_up_at` to `github_redeliveries`: `mode_set_by` records who last set the mode, `admin` for an admin's switch and `tiehall` for the credentials' storing, the check after the first installation and the fallback. It is a column rather than a read of the latest `github.mode_changed` event, because storing an App's credentials sets the mode with no event, so the latest event can name a switch made for an App the install no longer uses. An admin's switch (`github.set_mode`) and a verified delivery that `/webhooks/github` stores after the give-up clear `webhook_given_up_at`; storing new credentials clears it too, and sets `mode_set_by` to `tiehall`. The banner of the main change's 21.10 and 24.11 reads `webhook_given_up_at`, and the email is sent in the write that sets it, so later give-ups while it is set send none.
- **Why.** The job already counts the requests and reads the attempts; the switch reuses the mode's existing write and event, and the marker survives the pruning of `github_redeliveries`, whose rows go 3 days after the last request.
- **Alternatives.** A separate check that reads the whole log again, which costs calls for what the job already knows. Reading the given-up state from `github_redeliveries`, whose rows are pruned while the banner must stay.

#### T9. The default App name

- **Choice.** `defaultAppName` in `packages/commands/src/setup-github.ts` takes the recorded company name instead of the URL: "Tiehall", a space and the name, cut to 34 characters, with any trailing blank, dot or hyphen removed, as today. The App step's text before its button gains the way on for a taken name: GitHub's own page, or `TIEHALL_URL/setup`.
- **Why.** The App step comes after the company step, so the name is always there.
- **Alternatives.** Adding the host when the name is short, which brings back the length it removes.

## Risks / Trade-offs

- [A 30-day cap signs daily users out once a month] → The sign-in is one click on GitHub for a person already signed in there, and it re-runs the checks that matter.
- [Deleting deliveries loses what an admin might want to inspect after a week] → GitHub's own delivery log keeps them, and the activity log keeps what changed.
- [An HTML page hides the problem type from a person] → The page carries it in its markup, and any client that asks for JSON gets the problem.
- [The fallback to polling flips the mode while an admin fixes the webhook] → It does not undo an admin's switch to webhook mode, and the banner stays until an admin switches the mode or the webhook works again.
- [The invite form, its review page and its confirmation each read GitHub] → Invites are rare, and each read goes through a connected installation's token, outside any transaction.
- [A company name that GitHub refuses in an App name] → The name stays editable on GitHub's page and on the App step, and the App step says so.
- [The members of teams that mirror through GitHub see a banner they cannot act on] → It tells them why changes arrive late, as D28 #83 has for every integration banner; only admins get the email.
