# Design: Web UI design and the live hall

## Context

[proposal.md](proposal.md) says why the web UI gets a visual design and a live hall. This document restates the decision the specs rest on, D57, as public rules, each with its reason and the alternatives that lost; then says how each part looks and is built, what the live hall shows and where its data comes from, how it is tested, and what is left for the maintainer to approve. It cites nothing outside this repository.

**What exists.** The web role renders most pages itself, as HTML strings: `packages/commands/src/html.ts` (`htmlPage`, `PAGE_HEADERS`, the refusal renderer of `github-layer-hardening`'s D50 (7)) and the pages built on it, among them `home-route.ts`, `inbox-page.ts`, `request-lists.ts`, `new-request.ts`, `web-pages.ts` and `admin-pages.ts` (members and the admin pages), `admin-page.ts`, `github-admin-route.ts`, `activity-log-route.ts`, `apis-page.ts`, `email-settings-page.ts`, `sign-in.ts` (the sign-in page), `setup-route.ts`, `confirm-route.ts` with `reviews.ts` (the review pages and confirmations under `/confirm/…`), `consent.ts` and `device-approval.ts`. Their policy is `default-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, extended by `form-action` on the setup screen, the sign-in page and the consent screen, so no stylesheet, font or image loads, and no page links to another except the home page's list of links. The Next.js app renders a request's page and a team's intake page (`apps/web/app/[key]/page.tsx`, `lib/request-page.tsx`, `lib/intake-page.tsx`), which the proxy negotiates first (`apps/web/proxy.ts`, `request-urls.ts`) and which run the framework's scripts under a nonce made for each answer (`pageContentSecurityPolicy`), with styles `'self' 'unsafe-inline'` and images `'self' data:`. A path no route serves gets the framework's default not-found page, which carries an inline `style` element and `style` attributes and, because the proxy puts a policy only on the pages it negotiates (`passOn` in `proxy.ts` sets none), no policy at all; an error while a framework page renders would get the framework's default error page, which carries inline styles too. `/docs/api` renders Scalar's bundle under its own policy (`default-src 'none'`, `img-src 'self' data:`, no `manifest-src`), and `/docs/api/changelog` is plain HTML with one style element allowed by its hash. `/teams/apis` is no page: it only answers the posts of a team's intake page. Every page has the footer with the running version and its source link (`footerHtml`, `layout.tsx`). The browser tests run the installed Chrome through `playwright-core`; `packages/commands/test/web-ui-hosts-browser.test.ts` visits every route and fails on a request to another host, and names every route file under `apps/web/app` in its `PAGES`, `SIGNED_OUT_PAGES` and `NOT_PAGES`.

**The approved design.** The maintainer approved a design canvas of a brand board and five screens: the live hall, a request's page, the inbox, the setup screen and the form that opens a request. The canvas is kept outside this repository and is not needed: this document restates everything it fixes, the mark, the colors, the type and how each screen is laid out, as rules an implementer can build and test. Where the canvas shows something the domain does not record, such as an agent "pulling the packet", which is a read and leaves no event, this document says what is shown instead; where this document departs from the canvas, decision 3 under "Decisions to approve" names each departure. The canvas's colors were replaced on 2026-10-11 by its Navy & Gold board (D59), whose palette the tables below restate. The maintainer approved this change on 2026-10-12 (D61), with two departures from its recommendations, which this document now follows: the web UI sets its text in the system's own fonts rather than IBM Plex, and the top bar's New request is gold, as on the canvas.

**How the specs cite this document.** Every `Source:` line of an ADDED requirement cites D57 by its items, such as `D57 (9)`, then `design.md, Decisions this change rests on`, then the sections of this document under "Design", such as `design.md, Design: The content security policy of each kind of page`; a requirement that names a color of the palette also cites D59, and one that rests on a departure of the approval also cites D61. A MODIFIED requirement keeps the decision numbers its requirement cited before this change, adds the items of D57 it rests on, and names `design.md, Rules carried from earlier changes`, which says where its unchanged parts keep their sources.

**Constraints.**
- Nothing new loads from, calls or reports to another host (S13). The icons, the stylesheet and the live hall's script are served by the install, and text is set in the system's own fonts, which load nothing (Type).
- No new dependency and no install script.
- The pages that guard a decision, the review pages and confirmations, the consent screen, the device approval page, the setup screen and the sign-in page, run no script, as they do today; so do refusal pages.
- Updates reach the live hall by pull. No server-sent event stream and no WebSocket (requester-loop: No push paths other than the hooks), and no agent surface offers the live hall: its reads are internal commands of the web UI, as `members.list` is.
- No public contract changes: `/api/v1`, its OpenAPI document, the MCP tools and the packet schema stay as they are. The live hall's reads are internal commands of the web UI.
- Every operation the pages run still goes through `execute()`, as the web session (T3).
- A MODIFIED requirement repeats its heading exactly and keeps every scenario it had.

## Goals / Non-Goals

**Goals:**
- A web UI that reads as one product: one stylesheet, the mark, one type scale in the system's own fonts, one way of showing a request's state, and navigation between its pages.
- A live hall that shows, at a glance and as it happens, which teams ask which for what, where requests wait on a question, and which people and agents are at work, without showing anyone's text beyond a request's key and title.
- Pages that work on a phone, in a dark system theme, with a keyboard and a screen reader, and for people who ask for less motion.
- The same safety as today: no page runs more script than it does now, apart from the live hall's one script from the install, and nothing loads from another host.

**Non-Goals:**
- A theme or motion setting of the web UI's own; the system's preferences decide (D57 (5), (6)).
- A single-page client application, or client-side rendering of any page but the live hall's map.
- Translating the web UI; it stays in English, while text people write, Turkish included, renders in the system's fonts.
- The look of the API reference page at `/docs/api`, which Scalar draws under the policy the public-api capability defines. It is not a page of the web UI in the web-ui capability's sense; only its head changes, to name the icons, which its `img-src 'self'` allows, and not the manifest, which its policy would block.
- Push notifications in the browser, a sound, or a live hall for people who are not signed in.
- Showing reads. An agent that pulls a packet or reads a thread leaves no event (requests: The event log), so the live hall cannot show it, and this change adds no record of reads.
- Avatars from GitHub, which would load images from another host; people are shown by their login's initials.

## Decisions

### Decisions this change rests on

- **D57. The web UI gets a real visual design, with motion, and a live hall.** Taken by the maintainer on 2026-10-11, after opening an install in a browser and finding its pages bare, together with the approval of the design canvas and of the recommended defaults for the points the canvas left open. As public rules:
  - **(1) One look.** Every page takes its look from one stylesheet that the install serves, built on named design tokens. The light theme's colors are ink `#14161B`, secondary text `#4A5060`, line blue `#2B4ACB`, signal amber `#F2B33D`, ground `#F6F7F9`, surface `#FFFFFF` and border `#E3E6EB`; the dark theme and the live hall use dark counterparts, on the ground `#0E1117`. A request's state looks the same on every page. D59 replaced these colors with the Navy & Gold palette; the rest of this item stands.
  - **(2) The mark TM1.** In a 32 by 32 view box, with round caps and joins and a stroke of 2.5: the paths `M6.5 16 V7 L16 15.5 L25.5 7 V16` and `M16 17.9 V24`, and circles of radius 2.4 at (16, 15.5) and (16, 26.6). A sharp M sits on top; its middle vertex is a round junction ring, from which a T stem drops to a jack: a tie line between two switchboards. From afar it reads as a T, up close as an M.
  - **(3) Type.** IBM Plex Sans for text and IBM Plex Mono for keys, ids and code, both under the SIL Open Font License, served by the install itself. D61 replaced this item: the web UI sets its text in the system's own fonts, and the install serves no font.
  - **(4) A shell with navigation.** Every page shares a top bar with the mark; a signed-in member's pages link the live hall, the inbox with what waits for them, the requests, the members and, for admins, the admin pages. Pages where a person makes one decision or has no session show the mark and the name alone.
  - **(5) Themes.** The web UI follows the system's light or dark preference; the live hall is dark in both.
  - **(6) Motion.** Motion shows something that happens: a request moving along a line, an agent at work, a new entry. It stops under the system's reduced-motion preference, and repeating motion can be stopped.
  - **(7) Phone width.** Every page works at a phone's width.
  - **(8) Accessibility.** Text contrasts at least 4.5:1 with its background; actions are real buttons, controls have labels and the focus is always visible.
  - **(9) A policy per kind of page.** Pages load styles, fonts and images from the install only (D61 leaves fonts out: no page loads one). The live hall alone runs a script from the install (`script-src 'self'`); the pages the framework renders keep their nonce-bound scripts; review, confirm, consent, device, setup, sign-in and refusal pages stay script-free; no page can be framed.
  - **(10) The favicon and the app icon** are the mark, white on ink. D59 made them the mark in gold on navy.
  - **(11) The live hall.** A page where people watch requests flow between teams and see people and agents at work, animated. Every member sees it, as every member sees every request.
  - **(12) Live updates by long-poll.** The live hall reads its state and then holds a long-poll read in the style of the wait endpoint, on the web role, for a web session; no event stream, which the specs forbid, and no agent surface.
  - **(13) Names are untrusted.** The names of agent clients are data their clients chose, shown as text, as every name and title people and agents write.
  - **(14) Nothing from another host.** The install serves every asset the pages use, before setup completes too, so the setup screen has its look.
  - **(15) The request page shows who works on it.** A request's page says who wrote on it last, with their client, and lists what happened to it.
  - **Why.** Tiehall is used by people as much as by agents: they confirm commitments, answer questions and decide who works on what in the web UI, and a UI that does not read as a product is one they will not open. The live hall makes the product's idea, lines between teams that agents work on, visible in one look, which is what a team lead or a newcomer needs to trust it. The defaults keep every safety rule of the existing pages and add no new kind of channel, host or surface.
  - **Alternatives that lost.**
    - *Plain HTML as it is:* what the maintainer rejected.
    - *A CSS framework or CSS-in-JS:* a build step, class names in every page, and for CSS-in-JS inline styles, which need `style-src 'unsafe-inline'`.
    - *A client-rendered application for every page:* scripts on every page, the review pages included, against the rule that keeps them script-free.
    - *Fonts from a font host:* a request to another host on every page, against S13.
    - *IBM's font packages as dependencies:* they run IBM's telemetry tool when installed (Type).
    - *A server-sent event stream or a WebSocket for the live hall:* the specs forbid an event stream (requester-loop: No push paths other than the hooks), and a long-poll already serves the loop; a WebSocket is a second protocol through the operator's proxy.
    - *A live hall for admins only:* every member sees every request already (requests: Every member sees every request), so hiding the hall protects nothing.
    - *A theme switch:* a setting to store and a choice to make; the system preference is what people already chose.
    - *The canvas's "pulled the packet":* would need a record of reads, which the event log does not keep (Non-Goals).
- **D59. The web UI's palette is Navy & Gold.** Taken by the maintainer on 2026-10-11, after comparing three proposed palettes with this one on the design canvas and approving its board, "Navy & Gold", for every page. It replaces the colors of D57 (1) and (10); every other rule of D57 stands, the contrast, themes, reduced motion and phone width included. As public rules:
  - **(1) Navy and a broken gold.** The light theme sets deep navy ink (`#0B1B3A`) on a cool white ground (`#F6F7FA`); the dark theme sets light ink (`#E9EDF5`) on deep navy (`#0A1428`); the live hall is darker still (`#071026`), with a faint grid of dots. Links are navy blue (`#1F45A3`) in the light theme and light blue (`#9DB6EE`) in the dark one.
  - **(2) Gold only where attention is needed.** Gold `#E3B341`, a broken warm gold and never a lemon yellow, marks only what asks for attention: the needs-info lamps and chips, a page's main action, the inbox's waiting count, the mark, the dark theme's focus ring and notices, and the glow of a live hall panel whose team has a question waiting. A strong secondary action is navy (`#14306E` in the light theme, `#2A4A9E` in the dark one), with white text: the top bar's New request, which is on every page, and the moves of a request's state on its page; any other action is an outline. D61 made the top bar's New request gold, as the design canvas draws it; the moves of a request's state stay navy.
  - **(3) The mark** is gold on a navy tile (`#0A1428`) in the light theme and in the icon, the favicon and the app icon; in the dark theme, on the live hall and on the setup screen's dark art, it is navy on a gold tile.
  - **(4) Contrast holds.** Every pair of text and its background stays at 4.5:1 or more, and every pair of a shape that shows something and what it sits on at 3:1 or more, in each theme, as the stylesheet's test computes from the tokens. Which shapes those are is this change's reading of WCAG 2.2's non-text contrast (1.4.11), not part of the decision: the lamps, the edges of fields and outline buttons, a checked checkbox's or radio button's fill, the focus ring and the mark. A filled button is known by its label, which holds 4.5:1 on its fill, so its fill needs no 3:1 against the page: the light theme's gold main action is 1.8:1 on the light ground. Where a color of the board falls short, the token is the nearest color of the same hue that passes ("Decisions to approve", 3).
  - **(5) Lamps differ in lightness as well as hue,** for readers who cannot tell their hues apart: where the claimed, needs-info and done lamps come too close in lightness, the claimed or the done lamp is made lighter or darker in its own hue, and the needs-info lamp also blinks on the live hall. How far apart is far enough is not part of the decision; this change measures it in CIE lightness (L*), every two lamps of a theme at least 6 apart, and the needs-info and done lamps, gold and green, which red-green color blindness merges, at least 10, and puts that measure to the maintainer ("Decisions to approve", 3).
  - **Why.** The maintainer's research, as the board's notes summarize it: blue is the most-liked hue in survey after survey, and one warm accent on calm neutrals reads as trustworthy and keeps the accent meaningful; neon on black and purple gradients read as the look of every other AI product; and the old live hall's ground, `#0E1117`, matched GitHub's dark theme, so the hall looked like a GitHub page rather than Tiehall's own. Navy gives Tiehall a ground of its own, and gold, kept for what calls for a person, makes a waiting question the brightest thing on the page.
  - **Alternatives that lost.**
    - *Cobalt Current:* bright electric cobalt on a deep indigo ink ground, with tangerine only where a person is needed; the board's first proposal, on the same research (blue the most liked, orange the strongest attention cue for color-blind readers too). The maintainer chose the calmer navy and the softer gold over its electric blue and orange.
    - *Verdigris & Coral:* deep teal, like the patina on an old switchboard's brass, with warm coral for everything that needs a person; calm and fresh, and the hall that glows best, but on a trend color rather than the most-liked hue.
    - *Saffron Exchange:* an old switchboard with incandescent lamps: warm paper and warm black grounds, ember-orange buttons and saffron calling lamps. It catches the eye most, but its color family is the least liked in the research.
    - *Keeping D57's colors:* line blue and signal amber, on a dark ground that matched GitHub's.
- **D61. The maintainer approves this change, with two departures.** Taken by the maintainer on 2026-10-12, together with the pending decisions of the other changes in progress: every item of "Decisions to approve" goes with its recommendation, except items 4 and 5, which the maintainer rejected, and one part of item 3. As public rules:
  - **(1) The system's fonts.** The web UI sets its text in the system's own sans-serif font and its keys, ids and code in the system's own monospace font, through the stacks `system-ui, -apple-system, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif` and `ui-monospace, SFMono-Regular, Menlo, Consolas, "Liberation Mono", monospace`. The install serves no font file and no page loads a font, so the pages' policies allow none; the repository keeps no font files, and the license map gains no third-party folder. This replaces D57 (3) and takes the place of items 4 and 5, which are not built.
  - **(2) A gold New request.** The top bar's New request takes the style of a page's main action, gold with navy ink, in the light theme and the dark one, as the design canvas draws it, rather than the navy of D59 (2). The moves of a request's state on its page stay navy, and every other rule of D59 (2) stands; the rest of item 3 is approved as written.
  - **Why.** The maintainer's choice on reviewing the change. What it brings: (1) text shows at once in the font each system draws its own interface in, with nothing to download and no swap from a fallback font once a web font arrives, which moved the live hall's layout while its fonts loaded; no policy needs `font-src`; no third-party files or license to keep and update. (2) New request, the action that starts every request, looks the same as on the canvas the maintainer approved.
  - **What it gives up.** (1) One look across machines: the text is San Francisco on Apple's systems, Segoe UI on Windows, Roboto on Android and whatever the system names on Linux, each with its own widths, so no layout may rest on a font's metrics (Type). (2) A page with a main action of its own shows two gold actions, its own and New request in the top bar; on a request's page, posting stays the one gold action of the page's content.
  - **Alternatives that lost.** The recommendations: *IBM Plex Sans and Mono, IBM's unmodified files kept in the repository under the SIL Open Font License* (items 4 and 5), and *a navy New request*, a strong secondary action because it is on every page (item 3).

### Design

#### The install's assets

- **What.** The stylesheet `/assets/tiehall.css`; the live hall's script `/assets/hall.js`; the icons `/assets/icon.svg`, `/assets/icon-180.png`, `/assets/icon-192.png`, `/assets/icon-512.png` and `/favicon.ico`; and the manifest `/assets/manifest.webmanifest`. No font: text is set in the system's own fonts (Type).
- **Served to anyone, before setup too.** They hold nothing of the install, so they need no session and pass the setup gate, which serves `/favicon.ico` and every path under `/assets/` before setup completes; the setup screen and the sign-in page need them while nobody is signed in. An asset answer reads no session and sets no cookie, so it never renews a session either.
- **Headers.** The exact media type (`text/css; charset=utf-8`, `text/javascript; charset=utf-8`, `image/svg+xml`, `image/png`, `image/x-icon`, `application/manifest+json`), `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; sandbox` (which makes the SVG inert should someone open it as a page), and a strong `ETag` from the content's digest, with 304 for a matching `If-None-Match`.
- **Versions.** Pages name each asset with `?v=<digest>`; the stylesheet names no other asset, so it is served as its file is. An answer to a URL whose `v` is the current digest is `Cache-Control: public, max-age=31536000, immutable`; any other gets the current file with `Cache-Control: no-cache`, so a page from before an upgrade still gets a stylesheet and nothing stale is kept for a year.
- **Digests without a file read.** Every bundle that renders a page needs the digests: Next.js's server bundle, and `apps/server`'s `dist/main.mjs`, whose request guard renders the 413 and 503 refusal pages (`refusalAnswerAs` in `request-guard.ts`) and whose worker, migrate, admin and init roles import the same code. In `main.mjs`, `import.meta.url` names `apps/server/dist/`, not `packages/commands/`, and in Next.js's bundle it names a chunk, so neither can find the files by it. The digests are therefore a committed table, `packages/commands/src/asset-digests.ts`, which `pnpm assets:digests` (`packages/commands/src/write-asset-digests.ts`) writes from the files; a test recomputes the table from the files and fails on any difference, naming the command. Importing the asset module reads no file.
- **Files read lazily, in the web app only.** Only the asset route reads files, each on the first answer that needs it, and keeps it for the process. It finds them at `../../packages/commands/assets/` from the process's working directory, which is the web app's folder wherever the web app runs: `apps/web` under `next dev`, and the standalone server's own folder once it has started, because Next.js's standalone `server.js` changes into it (`/app/apps/web` in the image, `apps/web/.next/standalone/apps/web` in the test installs). `next.config.ts`'s `outputFileTracingIncludes` names `packages/commands/assets/**` for the asset route, so the standalone output and the image carry the folder at `packages/commands/assets/` beside `apps/web/`. Vitest's tests give the route its folder. An image test reads the assets from the built image before setup, and the browser tests read them through the test installs' standalone server.
- **`/favicon.ico`.** Next.js takes a route file at `app/favicon.ico/route.ts` for a static metadata file (`isStaticMetadataRoute`), so the asset route serves the icon file as `/assets/favicon.ico`, and `next.config.ts` rewrites `/favicon.ico` to it, query included; the setup gate, which runs before rewrites, passes `/favicon.ico` itself. The answer carries every header above.
- **Not found.** Any other path under `/assets/`, and any method but GET and HEAD, gets 404 `route-not-found`.
- **Where.** `packages/commands/assets/` holds every file, each one Tiehall's own. `packages/commands/src/assets.ts` holds the table of assets and the answer; `apps/web/app/assets/[...path]/route.ts` calls it.
- **Binary files and the repository's checks.** The source-citation check reads every tracked file, and every untracked one git does not ignore, as text, and looks for decision numbers such as `D57`; the bytes of an image can spell one. It skips a file that holds a NUL byte, as every PNG and ICO file does.

#### Motion and reduced motion

- **What moves.** Only what shows something that happens:
  - on the live hall: a line's dashes flow from the requesting team to the target team while one of its requests is `in_progress` (`cordflow`, 1.4 s, linear, repeating); a dot travels along a line when an event arrives on one of its requests (1.2 s, once), towards the team that did not act; a team node glows while one of its people or agents wrote within the last 60 seconds (`glow`, 2.4 s, repeating), in blue, or in gold while a question waits on the team; the `needs_info` lamp, and a request's `needs_human` chip, blink (`lampblink`, 1.6 s period, repeating); the three dots of an agent at work pulse (`typing`, 1.2 s, repeating) while their last event is under a minute old; a new feed entry slides in (`slidein`, 0.6 s, once); the "Live" lamp pulses (`livepulse`, 1.8 s, repeating);
  - on a request's page: the line between its two teams flows and the dots of a working agent pulse; on the setup screen, the switchboard drawing's lines flow and its lamps blink; in the inbox, a waiting proposal's lamp blinks and new updates slide in;
  - everywhere: hover, focus and the opening of a menu, at `--duration-fast` or `--duration`.
- **Five seconds.** On every page but the live hall, a repeating animation runs a whole number of times that ends within 5 seconds, then rests on its last frame; the words beside it, such as "working", stay. This keeps WCAG 2.2.2 (pause, stop, hide) without a control on pages that run no script.
- **The live hall without its script.** Its repeating animations run only once its script runs: the script puts the class `live` on the page's `body`, and the stylesheet runs the hall's repeating animations only under `.hall.live`; without the script, the hall's lamps and chips follow the five-second rule as every other page does. The Pause motion button is in the served markup with the `hidden` attribute, and the script shows it, so a page without scripts shows no button that does nothing.
- **The live hall's control.** A "Pause motion" `button` with `aria-pressed` in the toolbar stops every animation (it sets `animation-play-state: paused` through a class on the page, stops the dots' loop and starts no new dot), and starts them again. State changes, counts and new feed entries keep coming while paused; they just do not move.
- **How a dot moves.** A dot is an SVG `circle` that the script moves along its line's path: a `requestAnimationFrame` loop reads the position with `getPointAtLength` and sets the circle's `cx` and `cy` attributes. Never SMIL (`<animateMotion>`, which the canvas uses and which neither `animation: none` nor `animation-play-state` stops), and never `element.style`, which would leave a `style` attribute on the page. Pause motion and reduced motion stop the loop; a hidden page starts none.
- **Reduced motion.** Under `prefers-reduced-motion: reduce`, the stylesheet sets every animation to none and every transition to none on every page, and the live hall's script starts with "Pause motion" pressed and never starts a dot, a slide or a glow; changes apply at once.
- **No flashing.** Nothing blinks faster than once in 1.2 seconds, far under three flashes in a second (WCAG 2.3.1), and nothing flashes in red.
- **The browser.** CSS animations stop by themselves in a hidden tab; the live hall's script also starts no dot while the page is hidden.

#### Accessibility

- **Contrast.** Every text token pair in both themes and on the live hall is at least 4.5:1 (the tables above), the buttons, the inbox's badge and the live hall's initials and chips included, and every lamp, edge of a field or outline button, checked checkbox's fill, focus ring and the mark at least 3:1 against the background it sits on (D59 (4)); a filled button is known by its label, at 4.5:1 or more on its fill; the screenshot tests compute text contrast for every rendered text element (Testing).
- **Real controls.** An action is a `button` or a form's submit button; going to another page is an `a` with an `href`. No click handler on a `div`. The live hall's controls (the team filter, Agents only, Pause motion) are a `select` with a `label`, a checkbox with a `label` and a `button`.
- **Labels and errors.** Every field has a `label`; hints and the "required by FE" marks are tied to it with `aria-describedby`; a refused form shows the refusal in a `role="alert"` region at its top and names each refused field beside it, as the error model's per-field errors give them.
- **Focus.** `:focus-visible` draws a 2-pixel `--focus` outline with a 2-pixel offset on every focusable element, navy blue in the light theme and gold in the dark theme and on the live hall, at least 3:1 against the ground, the surface and `--surface-2`; nothing removes the outline. The keyboard order is the reading order; no positive `tabindex`.
- **Never color alone.** A chip carries its state's words, a lamp its count and state in words beside it, the inbox badge its count, and the live hall's legend names each color.
- **Structure.** One `h1` per page; headings in order; `header`, `nav`, `main` and `footer` landmarks; tables with `th` and `scope`; the mark, the switchboard drawing and the live hall's map `aria-hidden`, with what the map shows also in the page as lists.
- **The live hall for screen readers.** The feed is a list; a separate `role="status"` region announces "N new events on the line" at most once every 10 seconds, so a busy install does not talk over the person.

#### The content security policy of each kind of page

| Kind of page | Policy |
| --- | --- |
| A page the web role renders, other than the live hall: the home page, the inbox, the request lists, the new request form, members, email settings, connected agents and tokens, every admin page, the sign-in page, the setup screen, every review page and confirmation under `/confirm/…`, the consent screen, the device approval page, every refusal page | `default-src 'none'; style-src 'self'; img-src 'self'; manifest-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, with `form-action` extended as today: GitHub's web origin on the setup screen; on the sign-in page, GitHub's web origin and, while an agent client's authorization waits on sign-in, that client's registered redirect URI as its source, as the consent screen gives it (`sign-in.ts`); on the consent screen, the client's redirect URI as its source (its origin, or its scheme for an app's own scheme) |
| The API changelog page | the same, with `form-action 'none'` |
| The live hall at `/hall` | the first row, plus `script-src 'self'; connect-src 'self'; require-trusted-types-for 'script'; trusted-types 'none'` |
| The pages Next.js renders: a request's page, a team's intake page, the page for a path no route serves, the page shown when rendering one of them fails | `default-src 'none'; script-src 'nonce-<made for this answer>' 'strict-dynamic'; style-src 'self'; img-src 'self'; manifest-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'` |
| A JSON answer of the live hall | `default-src 'none'; frame-ancestors 'none'` |
| The assets | `default-src 'none'; frame-ancestors 'none'; sandbox` |
| The API reference page at `/docs/api` | unchanged, as the public-api capability and the main change's T10 define; its head names the icons, not the manifest |

- **Why these.** A page needs styles, images and its manifest, and only from the install. Without `'unsafe-inline'` for styles, text that reached a page as markup could not restyle it.
- **No font.** No page loads a font (Type), so no policy names `font-src`, and `default-src 'none'` refuses every font: a font that reached a page through its markup or the stylesheet could not load. The policies had `font-src 'self'` while the install served IBM Plex; D61 (1) dropped it.
- **The rule on `style` is on the served markup.** Every page is served with no `style` element and no `style` attribute, which the tests check in the HTML each page is served with. A script may still set an element's style through the CSS object model, which a policy without `'unsafe-inline'` allows and reports no violation for: Next.js's route announcer does, on the `next-route-announcer` element it adds (`app-router-announcer.js`), and the tests do not count it. While a page runs, the tests rely on the browser's own violation reports, which catch a `style` element or attribute added as markup; the live hall's script sets no style at all, which its browser test checks in the page's DOM.
- **The live hall's script.** `script-src 'self'` with no nonce: the page has one script, a file from the install, and no inline script at all. `require-trusted-types-for 'script'` with `trusted-types 'none'` makes every write of markup into the page, such as `innerHTML`, throw in browsers that support Trusted Types, so the script can only build elements and set their text; a test proves that the script never trips it.
- **The framework's pages.** They keep the nonce made for each answer and `'strict-dynamic'`, which every current browser honors, so the framework's own scripts run and nothing else; `'self'` is dropped from their `script-src`, where `'strict-dynamic'` already made browsers ignore it, so that `script-src 'self'` stands on the live hall alone. `default-src` becomes `'none'`, styles lose `'unsafe-inline'` and images lose `data:`. The framework's default not-found and error pages carry an inline `style` element and `style` attributes (`builtin/global-error.js`, `http-access-fallback/error-fallback.js`), so the app's own `app/not-found.tsx` and `app/global-error.tsx` replace them, rendered with the shell's classes; none of the framework's pages needs more.
- **Where the framework's pages get their policy.** The proxy puts the framework pages' policy, with a fresh nonce, on the request headers of every call it passes on (`passOn` in `proxy.ts`), from which Next.js takes the nonce for its scripts, and on the answer when the request's Accept header names `text/html`. A route handler's own policy replaces it on its answer: Next.js sets the proxy's answer headers before the route runs (`router-server.js`), and the route's own header overwrites them. So the page for a path no route serves, and the error page, which have no other way to get a policy, get this one.
- **What stays script-free.** Every page in the first two rows. That is where every decision is made, confirmations, approvals of agent clients and of the CLI, setup and sign-in, and where an agent that drives a browser would want a script to help it.
- **One place.** `html.ts` exports the policies as functions of the page kind, and every route takes its policy from there; `request-urls.ts`'s `pageContentSecurityPolicy` is one of them.

#### The request page's activity

- **The read.** `requests.activity`, an internal read that the web UI runs and no agent surface offers, defined in `packages/catalog/src/request-activity.ts` and handled in `packages/commands/src/request-activity.ts`, registered in `handlers.ts`. - **The page.** A banner under the header says, when an agent is at work, "<login>'s agent is working on this", with the client's name and the working dots, and in any case "last write <time> ago"; the timeline lists the 20 events with a lamp in the color, for the page's theme, of the state they left the request in, what happened, who and when, each time also as a `time` element with its ISO date. ##### Who is at work

- **From events only.** A person or an agent is at work on a request while the latest domain event on that request that names them as its actor is under 10 minutes old. The hall shows one entry per user, actor kind and client, with the request of that entry's latest event, newest first.
- **Actors that are not people.** The feed names the actor of every event: the user's login, with "agent" or "web", for those two kinds; Tiehall for `system` (such as close on merge); GitHub or Jira for `integration`, by the event's surface (`github` or `jira`); and "the operator" for `operator`. None of these is shown at work.
- **The client's name.** For an OAuth client identified by a Client ID Metadata Document, the `client_name` its document gave when it was fetched, with the document's host, which Tiehall verified; for a client registered through Dynamic Client Registration, the name it registered with and the mark "unverified", as the consent screen shows it (agent-access: The consent screen shows who is asking), or "unnamed client", marked "unverified", when it registered no name; for the `tiehall` CLI, "tiehall CLI" and its version from the event's client; for a personal access token, "personal access token". A name is cut to 40 characters and is always text: a DCR client can call itself anything, "Claude Code" included, which is why the mark is there.
- **People.** A login, its initials for the chip, and "(bot)" for a user an admin flagged as a bot. Tiehall shows no GitHub avatar, because it would load an image from GitHub.

##### Where its data comes from

- **Two internal reads**, `hall.state` and `hall.wait`, defined in `packages/catalog/src/hall.ts` and handled in `packages/commands/src/hall.ts`, registered in `handlers.ts`, offered on no surface (no REST path, no MCP tool, no CLI command), so the web UI runs them through `execute()` as the web session and no token can. Every member may run them; a removed member gets 403 as for every call (teams-and-roles: Membership is re-checked on every call).
- **The routes.** `/hall` renders the page from `hall.state` in a read-only call; `/hall/state` answers `hall.state` as JSON for the script; `/hall/wait?after=<cursor>` answers `hall.wait`. All three take `team` and `agents`. They accept only the session cookie: an `Authorization` header is not read, so an agent's token gets the same answer as no credentials: `/hall` a redirect to `/sign-in?return=%2Fhall`, the JSON routes 401 with an RFC 9457 problem. The JSON answers carry `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin` and `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`. Their field names are Tiehall's own and are not part of the public API.
- **The session is not extended by the hall's reads.** `/hall` renews the web session as opening any page does; `/hall/state` and `/hall/wait` read it without renewing it, as a server component does (`session-renewal.ts`). They are reads the page makes on its own, not uses by the person, and an unattended hall, such as one on a wall screen, would otherwise keep a session alive to its 30-day cap past the 7 days without use after which it expires (sign-in: Signing out and ending sessions). Once the session ends, the next wait gets 401 and the page says "Signed out".
- **`hall.state`** returns `now` (the server's time), `cursor` (the number of the newest domain event about a request), `teams` (key, name, counts by live state, done in the last 24 hours), `lines` (from, to, counts by state), `requests` (the 200 most recently changed live requests: `id`, key, title, state, from, to, claimant, `needsHuman`, `changedAt`), `atWork` (as above) and `feed` (the 50 latest events: `seq`, `at`, `type`, `requestId`, key, title, from, to, actor, `line`). It reads teams and live requests with their counts by grouping, the newest domain events by the event log's key in descending order, the events bounded by time through `events_domain_occurred_at`, each request's last change through `events_request_number`, and the users and agent clients they name, in one read-only transaction.
- **`hall.wait`** takes `after`. It runs in the step `execute()` runs before the call's transaction, as `events.wait` does (`packages/commands/src/events-wait.ts`): it takes a wake-up from `event-wakeups.ts`, reads in a short read-only transaction whether a domain event about a request exists after `after`, and if none, holds until the wake-up, the 25-second hold or the shutdown signal, reading again on its own every 5 seconds, as `events.wait` does (`RECHECK_MS`), in case a wake-up is lost with a lost listening connection; on a wake-up it waits 250 milliseconds more to gather a burst, then reads. The hold is a setting of its own, `WaitSettings.hallHoldMs`, beside the API wait's `holdMs`, which keeps its 60 seconds. It answers `now`, `events` (the new feed entries, oldest first), the current `requests` lines of the requests they name, with `terminal: true` for one that left the hall, the current counts of the teams and lines those requests involve, the current `atWork`, and `cursor`; with more than 50 events after `after` it answers `reload: true` and no events. Security events never wake it to an answer: they send no wake-up, and a wake-up that finds only events of no request holds on. While the app shuts down it answers 503 with `Retry-After: 0` at once.
- **Requests by id.** A reassignment gives a request a new key (requests: Reassignment gives a new key and the old key redirects), so both answers carry each request's `id`, and the script merges on it: a reassigned request moves to its new line, under its new key, and its old entry goes. A team's rename, a new team and a team's new key add no event about a request and send no wake-up; the page shows them when it next reads its state, which it does on load, after `reload: true`, and whenever an answer names a team the page does not have.
- **Why 25 seconds.** Under the 30 to 60 seconds after which common proxies and load balancers end an idle response, which an operator's own proxy may set, so a held wait ends on Tiehall's terms with a 200, not as a proxy's 504. The requester loop's wait keeps its 60 seconds, so a proxy in front of the install must let a response take at least 70 seconds (`docs/install.md`).
- **Alternatives.** *The public wait endpoint:* it serves one user's updates, while the hall shows every request, and it holds 60 seconds. *An event stream:* forbidden (Constraints). *Polling every few seconds:* slower, and more requests for the same result.

##### How fast it updates

- **The script's loop.** On start it reads `/hall/state`, draws, and waits on `/hall/wait` with the state's cursor; when a wait answers, it applies the answer and waits again at once from the new cursor. An event that commits while a wait holds reaches the page within the wake-up, the 250-millisecond gathering and a read, well inside 2 seconds; a lost wake-up costs at most the 5-second re-read.
- **When things go wrong.** A failed wait (a network error, a 5xx, a 503) is retried after 1 second, then 2, 4, 8, 16 and 30, each with up to 20 percent of random spread, and the live lamp says "Reconnecting"; a success resets the delay. A 401 stops the loop and the lamp says "Signed out", with a link to sign in again. A 403 stops it with the refusal's title. `reload: true` makes it read `/hall/state` again and redraw.
- **A hidden page.** On `visibilitychange` to hidden, the script aborts its wait and holds none; when the page is shown again, it waits from its cursor, which brings what it missed, or a reload when it missed more than 50.
- **Time.** Relative times ("now", "40 s", "3 min", "2 h") are recomputed every 15 seconds from each entry's time and the offset between the latest answer's `now` and the browser's clock, with no read; each is also a `time` element with its ISO date.
- **Caps on the page.** The feed keeps 50 entries; the map starts at most 8 dots at once and drops the rest; the at-work list follows each answer.

##### Many teams

- **The ring.** Teams sit on a circle in the order of their keys, evenly spaced, the circle's size from the map's box. Up to 8 teams: large nodes, 220 by 72 pixels, with the name, the key, the lamps and the counts. 9 to 20 teams: compact nodes, 132 by 56, with the key, the lamps and the counts, the name in the node's accessible text and in the list. The positions are computed so that no two nodes overlap at 20 teams in the map's box at a viewport of 1,280 by 800 CSS pixels, and a test checks it for every count from 1 to 20.
- **More than 20.** The map shows the 19 teams with the most live requests, ties by key, and one node "+N teams" that counts the others' live requests; lines to the others end at that node. Every team stays in the "Teams" list, and choosing one in the Team filter shows its lines in full on the map.
- **Lines.** At most one per ordered pair; with many pairs, the widths stay at 2 pixels for pairs of one request, so a dense map stays readable, and the "Lines between teams" table holds the detail.
- **Why a ring.** It needs no layout engine, gives every team the same place every time, and draws every line through the middle, where the flow is easy to follow; a force layout moves nodes on every change.

##### Its script

`packages/commands/assets/hall.js`, plain JavaScript in one ES module of its own, with no dependency and no build step. TypeScript checks it (`// @ts-check` with JSDoc types) through a project of its own, `packages/commands/assets/tsconfig.json`, which extends the base with `lib` `es2024`, `dom` and `dom.iterable`, `allowJs`, `checkJs` and `noEmit`, and includes only `hall.js`: the package's `tsconfig.json` includes only `src`, `test` and `vitest.config.ts`, and the base has no DOM types. The package's `typecheck` script runs `tsc -p tsconfig.json && tsc -p assets/tsconfig.json`. The script exports its pure parts, the ring layout, the curve of a line, the merge of a wait's answer into the state and the relative time, so Vitest tests them in Node; it runs them only when it is loaded by the page. It builds the map with `document.createElementNS`, sets every text with `textContent` and every class with `classList`, and moves dots as "How a dot moves" says, so under Trusted Types `'none'` nothing it writes can be markup and nothing leaves a `style` attribute. It is loaded with `<script type="module" src="/assets/hall.js?v=…">`.

#### How it is built

- **No CSS framework, no preprocessor.** One hand-written stylesheet, `packages/commands/assets/tiehall.css`, using custom properties, `:focus-visible`, `prefers-color-scheme`, `prefers-reduced-motion` and `forced-colors`, for the current versions of Chrome, Edge, Firefox and Safari. *Alternatives:* Tailwind, a build step and class names in every page's markup; Sass, a build step for features CSS now has.
- **Pages keep their renderers.** The string pages keep `htmlPage`, which gains the shell, the head links and the page kind's policy; each page's markup gains classes. The Next.js pages keep their server components and server actions; the layout gains the head and keeps the footer, and the pages render the shell; `app/not-found.tsx` and `app/global-error.tsx` replace the framework's defaults, which carry inline styles. The API changelog page's `style` element gives way to the stylesheet, which takes its rules.
- **One description of an event.** The feed, the request page's timeline and the inbox say an event in the same words, through `updateDescription`, plus who acted (`packages/commands/src/event-lines.ts`).
- **Dependencies.** None; the system's fonts need no files (Type). `pnpm-lock.yaml` and `pnpm-workspace.yaml`'s `allowBuilds` are unchanged.

## Risks / Trade-offs

- [The framework emits an inline style or script that the narrower policy blocks, and a page breaks quietly] → The browser tests fail on any violation the browser reports, on every page, the page for a path no route serves and the error page included; the app's own `not-found.tsx` and `global-error.tsx` replace the framework's styled defaults. A style the framework sets through the CSS object model, as its route announcer does, breaks no policy.
- [A long-poll per open live hall holds a connection, and a member with many tabs holds many] → A hidden tab holds none; a wait holds no database connection, as `events.wait` holds none; the hold is 25 seconds. The same holds today for agents on `/api/v1/events/wait`.
- [An open live hall keeps its session alive] → The hall's reads do not extend the session; only opening a page does.
