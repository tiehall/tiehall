# Tasks

This plan is ordered by milestone, never by week: M0 Foundation, M1 "It works", M2 The rest of v1, and M3 Release. Inside a milestone, groups follow their dependencies. Group and task numbers run on across the milestones (groups 1 to 30), and a plain line names each milestone before its first group.

How to read a task:
- Only checkbox lines are tracked. The checkbox line is the whole task as the apply step sees it: what to build, how it is verified (a test, a command or an observable result), and, in brackets at the end, the requirements it implements as `capability: Requirement name`. Indented bullets under a task are detail only, and plain lines are notes. The few tasks that no requirement covers name the design.md section they come from instead.
- Tests come first (TDD). When a task writes tests ahead of the task that makes them pass, it commits them as expected failures (`it.fails` or `test.todo`), so CI on `main` stays green; the implementing task turns them into plain tests and is done when they pass.
- A task marked **(founder step: …)** holds a step that only the founder can do, because it needs the founder's own accounts. The agent does and verifies the rest of the task, and the task is checked off once the founder's step is done too.
- A conditional task has an "otherwise" branch with its own verification, so it can be checked off either way.
- A task marked "(carried over from add-tiehall-beta task N)" was planned under the earlier hosted plan, and, where it is checked, finished there; its work is in the repository and holds for v1. That change stays out of the public repository.
- Where design.md lists a reading to confirm with the founder (R1 to R22), the tasks build the reading as written. A change to one changes only the tasks that name its requirements.

Founder steps that gate the plan:
- **A test GitHub organization and a second GitHub account**, with the founder signed in to GitHub in a browser, for the GitHub App spikes (1.5, 1.6), the plugin install check (17.7) and the real-GitHub runs (21.12, 23.19, 24.14, 30.6). The GitHub stub (7.3), which every later GitHub test uses, is built from the records of 1.5 and 1.6, so the GitHub work in M1 waits for them.
- **A Jira Cloud developer site** with a dedicated bot account and its API token, for the Jira spikes (1.7, 1.8), whose records the Jira stub (25.1) is built from, and the Jira run (25.15).
- **Real agent-client sessions** on the founder's own Claude Code, Cursor, Codex and Copilot accounts: the open spikes (1.3, 1.4), the plugin URL spike (1.9), the plugin and skill checks (17.7, 17.8, 29.6), the hooks (19.19, 19.21), the M1 run (21.12), the client matrix (group 27) and the clean-machine install (30.6).
- **npm**: the placeholder publish that reserves the `tiehall` name and the `@tiehall` scope, and the trusted-publisher setup, before the first publish (29.4).
- **Making the repository public** (30.3 to 30.5): permission for the history rewrite and its force push at that time, the choice of the author identity the public history shows, the repository settings, and the switch to public.
- **The `tiehall.com` domain and its hosting**, only when the packet schema is published (29.13).

Not in v1, and so not in this plan (design.md, Goals / Non-Goals): passkeys, SSO, the agent-client allowlist, the anchored tamper-evident audit log, several orgs per install, billing, and running a hosted service.
