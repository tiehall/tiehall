# Tasks

One group, in milestone M3 "Release" of the main change, `add-tiehall-oss-v1`, built before its group 29 publishes the first release. This change waits for the maintainer's approval (D55): none of its tasks is built until the maintainer has approved it, and an item the maintainer changes in "Decisions to approve" changes the task that builds it. Tasks 1.1 to 1.17 cover the items where the code already does what the new rule says and the spec only catches up (D55 (2), (10), (13) to (17), (20) to (22), (27), (29), (31) to (35), (40), (42), (45), (46), (49), (51), (53), (57), (59), (72), (73), (75), (77), (78), (84) and (85)): each names the tests that cover its rule and writes the ones that are missing, as plain tests, because the behavior exists; they change no behavior, except 1.7, which adds a sentence to a page. Tasks 1.18 to 1.58 change code, tests first, and 1.59 waits for a founder step. Task 1.60 applies the text corrections, and 1.61 checks the change itself. Their order: the error model's `busy` row (1.18) comes before the other tasks that name the error model's rows; the label case of 1.29 before 1.30 and 1.31, which use it; the scope of a user's updates (1.35) before the cursors (1.36), the digest (1.37) and the team digest (1.47); the CI caller (1.42) before the Action (1.44); and the deprecation of `providerChange.api` (1.54) at least 14 days before its removal (1.55). Some cases extend main tasks that are not built yet: the Jira halves (group 25), the client matrix (group 27), the release workflow and its notes (29.1, 29.2) and the new-tool-name rule of 29.15; those cases are written with those tasks, and where a main task's text differs from this change, this change's tasks govern. When a task renames or adds a test that `tools/repo-checks/security-events.json`, `confirmation-actions.json` or `error-model-tests.json` names, it changes that file in the same commit, and `pnpm check:security-events`, `pnpm check:confirmations` and `pnpm check:error-model` still pass. A task that changes a public contract regenerates `openapi/v1.json` (`pnpm openapi:generate`), the MCP tool snapshot (`pnpm mcp:generate`) or the packet schema (`pnpm packet:generate`) in the same commit, with its changelog entry, and `pnpm check:openapi`, `pnpm check:mcp-tools`, `pnpm check:packet-schema`, `pnpm check:api-compat`, `pnpm check:tool-compat` and `pnpm check:packet-compat` pass.

Tasks read as in the main change's tasks.md: the checkbox line is the whole task, with how it is verified and, in brackets, the requirements it implements; tests come first and are committed as expected failures (`it.fails` or `test.todo`) until the task that makes them pass.
